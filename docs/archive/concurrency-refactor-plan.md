# 并发改造计划

> 历史归档（2026-11-04）。正文保留当时的方案或执行状态，不代表当前版本；日常操作见[文档入口](../README.md)。

日期：2026-10-09。目标：在**不动业务流程、不引入中间件**的前提下，让多用户多任务安全并行。
风格约定：只改**调度策略**，用**现有 Job 记录**承载一切；新增字段一律可选，旧数据兼容。

---

## 0. 目标

> **让"等待"不再占用"干活"的位置；同一项目内部串行，项目之间按资源类型并行。**

## 1. 三条不变量（改完必须一直成立）

1. **同项目串行**：同一时刻，一个 batch 只有一个执行器。
   （`results.json` 是裸写，多个执行器会丢更新。）
2. **等待不占执行位**：下载、等 FBBM、等人审片都是"等待"，不占 CPU 位置。
3. **每一步可重入**：任何阶段中断后，能从该阶段重排、安全重做。

---

## 2. 改前 / 改后

| | 现在 | 改后 |
|---|---|---|
| 调度单位 | 整个 `produce` / 整个 `publish` | 拆成阶段：`fetch` `render` `upload` `poll` |
| 并行控制 | 全局 1 个（有活动就 return） | 按 **lane** 计数，`continue` 不挡别的 lane |
| 等 FBBM | 子进程里 `sleep(15)` 循环，占位 | 单次查询，查完写 `not_before` 回队列，不占位 |
| 崩了怎么办 | 多数标"中断，请重做" | 从最后未完成阶段续跑 |
| 磁盘 | 开工前看一次剩余 | 上工位前**预约** |

---

## 3. 六个改动

### 改动 1｜给任务分 lane（分级）
每个 job 打一个 `lane` 字段（复用现有控制记录里已有的 `lane` 概念）：

| lane | 干什么 | 资源 |
|---|---|---|
| `fetch` | 准备正片 | 网络 |
| `render` | 剪辑、Hook、QC、预览 | **CPU + 内存** |
| `upload` | 传 OSS + 建飞书记录 | 网络 |
| `poll` | 单次查询 FBBM | 外部 API（短） |

### 改动 2｜阶段推进器（核心，也最优雅）
**一个阶段完成时，由它决定并投递下一个阶段。** 不需要通用 DAG 引擎：

```
fetch 完成   → 投递 render
render 完成  → 批次转 review（等人）
人确认上传   → 每投递一个 upload
upload 完成  → 投递 poll（not_before = now + 15s）
poll 未就绪  → 把 poll 用 not_before = now + 下一个间隔 重新入队   ← 等待不占位的关键
poll 就绪    → 该条完成
poll 失败    → 标记失败，可人工重试（重新投递 poll）
```

`poll` **不再 sleep**：它查一次、写结果、退出；什么时候再查由调度器按 `not_before` 决定。

### 改动 3｜调度器从"布尔串行"改成"按 lane 计数"
把 `worker_tick` 里的 `if running: return` 换成：

```
for job in ready_jobs(ordered_by_owner_fairness):
    if active_count[job.lane] >= capacity[job.lane]:
        continue                      # 一个 lane 满，不挡别的 lane
    if batch_has_running_job(job.batch_id):
        continue                      # 不变量 1：同项目串行
    if not reserve(job):              # 改动 6：磁盘/内存预约
        continue
    start(job)                        # 落盘 admission → 起子进程
    # 继续尝试下一个，直到所有 lane 满或 ready 耗尽
```

`reconcile`（暂停/恢复）同步改成**按 lane 空位恢复**，不再"只恢复一个 / 有活动就忙"。

### 改动 4｜拆分两个长等待
- **发布**：`workflow publish` 拆成 `upload`（传完即退）与 `poll`（单次查询）。
  现有 `_publish` 的循环改成一次 `sync_record_once`。
- **制作**：`produce` 里先跑 `fetch`（复用现有 `source_prefetch`），正片齐了再进 `render`（纯剪辑）。
  制作启动时若源缺失，投递 `fetch`，不再在 CPU 位上偷偷长下载。

### 改动 5｜阶段结果（可恢复）
每个 job 结束写一条不可变结果（输入指纹 + 产物校验值）。恢复时：

```
recover():
  for job in 未完成:
    if 进程还活着(现有 process_token + instance + ps 校验): 认领
    else: 从该阶段重排        # 每阶段可重入：render 复基底、upload 核 OSS、poll 复用记录
```

`recover_jobs` 改为**每 tick 全量收割**，不再依赖"owned 为空"。
页面状态由**阶段结果**派生，而不是"进程活着/死了"。

### 改动 6｜磁盘预约 + 交付保险
- **预约**：启动前按文件系统（`st_dev` 归并）预留峰值空间；失败释放、结束核销、重启重建。替换现在"只看一次剩余"的 `require_space`。
- **交付保险**：`upload`/`poll` 先落"意图"（目标对象、已批准 sha、记录 id 或"待核实"），再执行，再核对；结果不明 → `待核实`，**不自动重放**。

## 4. 容量（新配置 `concurrency`，全部可选）

| lane | 生产值 | 安全默认 | 依据 |
|---|---|---|---|
| `render` | 3 | 1 | 14 CPU / 24 GiB；每个 ffmpeg `-threads 4`，合计 12 线程不超订 |
| `fetch` | 2 | 1 | 带宽（实测约 5 MiB/s） |
| `upload` | 2 | 1 | 上传带宽、OSS 配额 |
| `poll` | 不限（很短） | 1 | 单次调用 < 1s，按 `not_before` 定时，不占位 |
| `ai` | 令牌桶 | 令牌桶 | 供应商配额（覆盖所有 AI 入口） |

- 生产容量见 [服务器规格](server-sizing.md)：宿主 16 vCPU / 约 30 GiB，容器 `cpus=14 / mem=24GiB`。
- `pids_limit` 需从 256 调高到 ≥512（线程计入）。
- 全局活动子进程数仍受内存与 `pids_limit` 双重约束。**安全默认全部为 1 时，行为≈现在的串行**（回退安全）。
- 全局上限 `max_active_children` **不写进生产配置**：留空即自动 = 各 lane 之和（改 lane 时自动跟随，不会遗忘）；**仅在应急降级时**显式写一个更小的值。不要把它当成需要手工维护的数字。

## 5. 落地三步

### 第 1 步｜解决痛点（最高性价比）
- 改动 1 + 2 + 3 + 4。
- 结果：**A 等 FBBM / 下素材时，B 能上剪辑位**；不动共享归属那套复杂协议。

### 第 2 步｜防崩
- 改动 5 + 6。
- 结果：崩溃可从断点续；磁盘不超卖；外部写不重复。

### 第 3 步｜打磨
- 公平轮转、排队可见性、容量按双任务实测标定。
- 明确后移：媒体探测缓存、抽帧/缩略图、QC 缓存、镜头索引并发生成。

## 6. 测试与验收层级（TDD）

所有改动**测试先行**：先写失败测试（红）→ 最小实现转绿 → 重构。新增单元必须有独立单测。

| 层级 | 范围 | 手段 | 通过标准 |
| --- | --- | --- | --- |
| 单元 | lane 准入、阶段推进器（含 `not_before` 重入）、同项目串行、磁盘预约/释放、身份认领与断点重排 | `pytest`，短流程，无外部依赖 | 全绿，含"容量全 1 回退"用例 |
| 集成 | 一个 batch 走完 fetch→render→(确认)→upload→poll；两用户并行互不阻塞；等 FBBM 不占 render；崩溃从断点恢复；暂停/归档不影响他人 | 独立临时数据根 + 模拟外部客户端，不发真实请求 | 端到端通过 |
| macOS 开发环境 | 在本机 macOS 跑完整 `pytest` | 隔离环境变量与数据根 | 全绿，无回归 |
| 线上真实环境 | 已提交版本经发布管理器部署到美东实例（`8.221.122.75`，14 CPU / 24 GiB） | 真实两用户并发、等 FBBM 不占位、重启恢复 | 记录证据（时间/命令/观察） |

边界：**不得在生产目录开发**；发布与回退走现有 release 管理器与维护流程；生产验收若缺凭据，必须产出可执行步骤与证据模板并标注"未执行"。

---

## 7. 验收（每一步都要过）

- A 长时间等 FBBM 时，B 能制作/上传；
- 两用户制作同时存活（`render` 容量 > 1 时）；
- 一个用户连续提交不挡其他用户；
- 同一项目任何时刻只有一个执行器；
- 同集只下载一份；同基底只生成一次、不同 Hook 独立成片；
- 重启不重复启动 / 不重复上传；
- 外部结果不明时进入"待核实"，不自动重放；
- 把容量全设 1，旧任务与旧行为仍可用。

---

## 8. 回退与兼容

- **纯增量**：新增字段（`lane`、`not_before`、`result`）全部可选，旧记录照常跑。
- **一键回退**：`concurrency` 全设 1 → 回到串行；或关闭开关，只走旧的 `produce`/`publish` 路径。
- **不改数据 schema**：仍是每项目 JSON；`schema_version` 不变。
- **不改外部契约**：OSS/飞书/FBBM 的调用方式不变，只改"什么时候调、调几次"。

---

## 9. 为什么这样最优

- **只改调度策略**，不改业务流程 → 风险最小、可增量上线。
- **阶段推进器**取代通用 DAG 引擎 → 概念最少，行为最直观。
- **等待回队列**取代 `sleep` → 根治"等待占位"，且天然抗重启。
- **每阶段可重入** → 不需要复杂事务，就能断点续跑。
- **默认容量 1** → 任何一步出问题都能立刻回退到今天的稳定行为。
