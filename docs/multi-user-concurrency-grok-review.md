## 逐项核对与设计修订

| 审查项 | 核实与处理 |
| --- | --- |
| 共享下载挂在发起 batch 下 | 成立：现有 prefetch 带 batch_id，批次控制发送进程组信号。补独立共享工作、订阅集合、最后订阅者取消、身份核验后终止、独立进度投影及恢复规则 |
| 暂停保留共享独占锁 | 成立：renderer 的锁覆盖基底和 Hook；SIGSTOP 不释放锁。共享基底写工作与私有 Hook 分开，私有工作在无写锁/许可的安全点自行暂停，避免父进程检查后再停止的竞争窗口 |
| 正常 FBBM 等待被收尾为中断 | 成立：finish_job 在进程退出且 runtime 仍 active 时可写 interrupted，恢复也会将没有进程的发布态判失败。补阶段结果协议、正常无进程等待、单次查询结果映射、持久截止时间和外部结果待核实 |
| 接管后的进程收割依赖 owned 为空 | 成立：worker_tick 仅在 not owned 时再次 recover_jobs。设计改为统一记录、每 tick 收割，按 job/阶段计占用，兼容仍在内部轮询的旧 publish 执行器 |
| 同时申请磁盘缺预留账本 | 成立：require_space 只查看当时 free。补实际写工作归属、按文件系统归并、峰值与已落盘差额、启动窗口恢复和扩预算准入；私有成片额度也要单独计 |
| 暂停任务绕过队列上限 | 成立：现有 queue_size 排除 paused/archived。补用户未完成工作上限、暂停常驻上限与制作常驻总量、共享工作记录上限，周期查询复用已有条目 |
| 基底只存在 MP4 时如何处理 | 当前 renderer 已在独占锁内核对 meta、identity、摘要及时长；缩锁和阶段拆分后仍必须保留该验证。补共享读锁内再次核验、生成中不命中、使用期锁及使用时间更新 |
| AI 限额跨进程没有完整协议 | 初稿只有原则。补实例级许可覆盖所有 AI 入口、缓存命中免许可、后台返回资源等待、Web 繁忙可重试、退出/接管释放或重建许可 |

## 未直接采纳的建议及补充证据

- **命名锁已覆盖确认流程。** `workflow.start_batch` 在 `naming_lock` 内调用 `_start_batch`，覆盖重名扫描和 `confirmed.json` 写入；这部分未完整提供给 Grok，因此不能把其推演的“两次确认无锁”当成现有缺陷。保留该锁，另外测试并发确认和目标对象归属。
- **对象已存在不一律拒绝。** Grok 建议本地没有记录 ID 时拒绝已有 OSS 对象，会阻断“上传成功但结果未落盘”的恢复。修订为外部写前保存本条发布意图，核对对象摘要和唯一匹配记录；归属不明、多匹配或结果不明时待核实，禁止直接接上他人的记录。
- **无配置与非法配置分开。** 无并发配置保持全局 1；非法值阻止启动并明确报错，沿用现有配置验证习惯，不静默回串行掩盖错误。
- **实例标记已有稳定依据。** `runtime.instance_marker` 是绝对 data_root 的摘要，不随同数据根下的 Web 重启或代码版本变化。`batch_control.LOCK` 已是 RLock，不需要新增替代锁。搬机器不继承活进程身份。
- **项目 owner 已存在。** `accounts.owner` 读取 batch 的 `access.json`，旧项目回退 admin，不新增一套归属字段；actor 只审计。
- **缓存复用已有锁内二次判断。** `_ensure_one` 在 episode 独占锁内调用 `_usable`，Grok 的相关不确定性来自摘录范围。需要修改的是“完整缓存也先拿独占锁”的效率与并发边界，不是从零补锁内校验。
- **删除已有公共素材边界。** `workflow.delete_batch` 的说明和实现只清理 batch、关联任务及导入请求目录，不删剧级公共素材。新增共享工作后还要让 batch 删除不杀其共享写者、不移除其他订阅者的结果和日志。
- **暂停内存不是只加一个数量常量。** 除常驻暂停上限外，制作的常驻总量同时包含运行和暂停进程，并需总内存准入；SIGSTOP 不等于内存释放。

## 实现前验收要求

设计中的验收矩阵已增加：三用户同源与发起者退出、共享写者崩溃和不完整 meta、安全点暂停、接管进程独立收割、正常 FBBM 无进程等待、quota_deferred、外部写结果丢失、跨项目发布归属、同盘预留差额、暂停配额以及统一 AI 许可。

媒体探测持久缓存、抽样帧、整条成片/跨项目 QC 缓存、镜头索引并发生成和空闲额度借用可后移。未测前不扩大 FFmpeg 线程与 pids_limit，不引入跨机租约、Redis/Celery 或新 env 体系。

本文记录的是对原稿的实际审查及人工核对；修订后的[设计稿](multi-user-concurrency-design.md)尚未取得第二轮 Grok 通过结论，也没有以测试证明并发可用。后续实现须先建立隔离回归和内部操作契约，再逐步启用额度。
