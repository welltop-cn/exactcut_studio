## 攻击与故障场景

1. **将凭据或带签名 URL 放进错误文本**：环境值遮盖新增 WEBHOOK，告警格式再去除机器人地址、URL 凭据/query/fragment、令牌和本机绝对路径。回归检查消息及 SQLite 文件不含合成私密值。未增加任意 provider 响应或业务表单正文采集。
2. **伪造脱敏器占位符**：原监控移用的 NUL 索引标记可被错误文本中的同形字串干扰，复现为 IndexError，可能导致该事件无法入队。新格式器先剔除输入 NUL，再创建自己的占位符；先失败后通过的回归已加入。旧独立监控格式器未在本分支额外改动。
3. **利用目标 URL 或 HTTP 重定向外传**：默认环境关闭；实际请求先执行既有 `require_external()`，再限制官方 HTTPS host、端口、v2 hook 路径，拒绝 userinfo/query/fragment 与跳转。测试覆盖隔离环境即使有开关也不发送，以及非官方地址、HTTP 和 query 的拒绝。
4. **慢飞书请求阻塞制作**：网络只在发送线程发生，发送时不持有数据库事务。使用阻塞的模拟发送器证明另一事件仍可入队；第二发送器拿不到发送锁而退出。SQLite 本地锁最多等待 50ms，磁盘耗时不是硬实时保证。
5. **发送失败或进程中断丢通知**：先将合并文本与计数消费写入同一事务；网络成功后删除 outbox。失败后重新创建队列对象可补发；提交成功后中断可能重复，采用至少一次语义。
6. **错误风暴放大磁盘/消息量**：1,000 签名、100 条通知、有界字段、每条 12KB、每轮至多十类；超出单条消息的类别留待后续轮次，现有积压不删除。新签名超容量时仅降级 stderr，仍可能丢失该告警，见限制。
7. **将版本冲突/资源暂忙当成系统错误**：补充交互队列告警时识别明确的 CutError 409/429，仍记 warning；取消和 ResourceDeferred 保留原处理。三种执行结果的回归先发现误告警，随后修复。
8. **恶意本机用户替换状态为符号链接**：直接目录/数据库/发送锁拒绝符号链接，初始私有权限；依赖可信数据根和父目录。没有声称抵御可写同 UID 数据根的恶意管理员，也没有改账号鉴权。

## 剩余边界与上线前事项

- 当前没有真实飞书群接收证据；需要受控启用现有生产 webhook 并发送明确的测试事件。
- 现有 healthz 不检查飞书发送器或积压。队列初始化/发送失败通过有限频的 stderr 记录，服务健康不等于通知正常。
- warning/未记录诊断的其他业务失败不被统一升级；这次明确补了交互异常路径，未宣称覆盖所有业务状态。
- 队列故障时业务继续，告警可能入队失败；默认限制和至少一次语义见应用告警文档。
- 旧 scanner 的 outbox 和冷却签名不会自动迁移；切换须确认处理旧积压、停用 log_feed、保留外部健康与资源检查。回退不恢复旧业务数据库。
- 默认 false；本轮未改生产配置、凭据、cron、应用进程或部署记录。代码审阅通过与生产上线是独立步骤。
