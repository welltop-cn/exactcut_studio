## F9 — P1：单条报告错误扩大为交互队列故障

### 复现与影响边界

使用两个独立任务，损坏第一个任务的报告，要求第二个正常任务仍能完成。

- JSON 破损：逐条取消检查或恢复检查抛异常，正常任务轮次无法继续。
- JSON 是列表：代码继续当字典使用，可使调度线程退出。
- status 为列表：集合判断抛 TypeError，可使调度线程退出。
- 报告 id 与持久描述符不符：旧代码仍可能将该任务交给执行入口。测试只证明错误记录进入本地执行回调，不将其扩大为已绕过真实媒体或外部接口的全部保护。

以上分别在 pending 状态，以及真实子进程完成 claim 后直接退出的 active 状态验证。未注入运行中的生产或可见测试实例，没有发现真实线上损坏记录，也没有统计此问题的生产频次。

### 根因与修复

`interactive_queue.Dispatcher.recover`、`finish_cancellations`、`claim` 直接读取并使用单条报告；异常隔离在整个调度轮次之外，无法隔离出错的那一条。相关读取可追溯至 `abd089f`，属于原复盘范围里的持久交互队列代码；之前 worker 坏任务修复没有覆盖这个独立队列。

增加集中、只读的报告检查：

- 报告文件确实不存在：沿用已有 outbox 描述符，允许正常的登记/报告发布中断恢复。
- 文件存在但无法读取、不是字典、任务 id 不匹配、status 类型不正确：不覆盖报告，不执行该任务，不用旧描述符假装已知道执行结果。
- 在恢复、取消检查、准入时跳过无法安全读取的报告；保留任务描述符和原报告，让其他任务继续。

损坏任务自身仍需人工核查，不是自动修好了损坏数据。完整 queue.json 或描述符本身损坏不在这次修复范围；执行过程中新发生的任意磁盘故障也没有被穷尽验证。

### 真实进程退出对照

新增子进程在 queue 描述符已持久化、报告尚未发布时 `os._exit(72)`。新调度器无需手动重新提交，就能重建报告并执行一次，结束后 pending/active 都为空。

另一组子进程在 claim 完成后 `os._exit(71)`，验证操作系统释放真实文件锁后恢复路径能隔离坏报告。这个窗口是 claim 后、执行回调前，不冒充真实视频渲染中途崩溃测试。
