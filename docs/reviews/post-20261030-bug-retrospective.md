## 二、本轮发现的当前缺陷

### F1 — P1：默认续传 HTTP 适配器把 headers 字典当字节偏移

位置：`source/exactcut/originals.py:268`、`:274`、`:285`；入口为 `source/exactcut/webserver.py:1582` 的原片 `/file` 代理下载续传。blame 明确指向 `faf29bc`。

`_get_stream(url, start=0)` 的第二参数是偏移；`open_original()` 却调用 `get(url, {'Range': ...})`。因此 start=100 的实际默认请求为：

```text
预期 Range: bytes=100-
实际 Range: bytes={'Range': 'bytes=100-'}-
```

触发条件：原片代理下载已经发出部分字节，上游流中断，进入默认 resume。它不影响一次完成的正常下载，也不是生产 OSS 上传开关失效。

本轮保留真实 `open_original` 和 `_get_stream`，只替换签名返回与 requests.Session 的网络出口，记录实际 HTTP headers；模拟上游拒绝非法范围后得到 OriginalsUnavailable。没有向真实 OSS 发请求，没有证明生产发生频次。

已有 `test_originals_resume.py` 三项回归仍 **3 passed / 0.33s**。它们替换 resume 或 `_get_stream`，替身的第二参数恰好接受 headers 字典，因而遮住真实默认适配器的参数错配。另一个成功流夹具宣告长度 15，却拼出 `firstsecondthird` 16 字节，也说明当前测试未约束实际协议一致性。

建议修复：统一 getter 的参数契约，使用明确的偏移参数；增加保留默认 adapter、仅替换网络出口的测试，断言真实 Range、连接关闭对象与输出字节。进一步补 206 Content-Range 起点/总长、对象身份变化和短读/多读测试；后几项是条件风险，不声称已观察到线上文件损坏。

### F2 — P2：Hook 展示缓存没有覆盖所有输入变化与晚到响应

位置：`source/exactcut/web/app.js:27`（watchHookJob）、`:37`（接受条件）、`:284`（invalidateHook）、`:554`（saveCurrent）、`:600`（结构化片段输入）。

**场景 A：修改并保存后，晚到的旧结果重新出现。**

1. 针对旧草稿发出 Hook 状态请求，服务端生成 `input_current=true` 的响应。
2. 响应到达前，用户修改并成功保存。`saveCurrent()` 将 dirty 清为 false，当前内容已经不同。
3. 旧响应到达；watcher 只检查项目 ID、request_id、响应里的 input_current 和当前 !dirty，没有检查该响应对应的本地输入代际。
4. 旧预览写入 hookPreviews。

本轮执行真实前端函数，受控推迟响应，并模拟已成功保存的当前状态，得到 revision=2、新 Hook 文案、dirty=false，同时 acceptedOldKey=old-preview-key。此检查没有走真实 Chrome/HTTP 保存链，结论限定为生产函数在所列状态交错下接受旧结果。`controls()` 允许 Hook 后台处理中继续编辑，保存路径没有因 watcher 阻止保存，因此状态交错有实际入口。

**场景 B：修改结构化片段时间，旧预览直接保留。**

真实 requests input handler 的 data-clip-part 分支只调用 changed、refreshClipTiming 和 refreshSegmentDurationNotices，没有调用 invalidateHook。把 start_s 从 00 改为 10 后，dirty=true，但原 hookPreviews 和 preview_key 仍存在。对比之下，修改 timeline_text、Hook 文案、添加/删除片段都会显式 invalidateHook。

两个场景共同说明失效逻辑依赖零散事件分支和一个 dirty 布尔量，不能完整表示“预览仍对应现在的输入”。场景 A 的旧接受条件来自 `abd089f`；11 月 10 日移除草稿回写后它仍保留。场景 B 的遗漏是当前存量缺口，本轮未将引入时间归因给 11 月 10 日修复。

建议修复：以项目、素材 request_id、影响预览的输入代际关联展示结果；用户修改相关输入时统一失效，回包前复核代际和最新任务身份。无需把全项目 revision 当作唯一失效键，否则无关素材状态变化又会过度失效。保存后 dirty=false 不代表旧输入重新有效。

后端 `hook_preview.state()` 和 `bind_confirmed_previews()` 仍检查请求、配置及源身份。本轮没有发现上述展示错误能直接绕过这些检查；不能扩大成“已确认正式成片错误”。同时，也不能把后端保护当作展示层无需修复的理由。

## 三、为什么已有大量测试，仍然漏掉

1. **测试替身截断了需要验证的边界。** F1 的默认 HTTP 适配器没有被走到；接口间的参数错误在每个替身测试里都表现正常。新测试要把替身下沉到网络出口。
2. **测了状态，未测足状态顺序。** “晚到时 dirty=true”已覆盖；“修改→保存→dirty=false→旧回包”没有。10 月 31 日的原 29 项专项测试同样漏掉“放弃与确认交错”和“拒绝后恢复旧报告”，父级补测才出现 2 failed。
3. **分支分别成立，不代表合并后成立。** `de8d7e7` 是预取锁与后来任务读取锁的组合回归。空任务目录不会进入第二把锁，顺序用例也不会暴露它。
4. **新的数据/对象语义没有覆盖旧记录和旧持有者。** 指纹升级后旧等待失效、读缓存改成独立副本后 resident job 脱节，都是跨版本/引用契约问题。
5. **媒体验证的参考与平台语义也会错。** PSNR 的比较范围、复制帧真值、1/2 帧 DTS、视频时长与音频时长都必须显式区分；仅“命令成功退出”远远不够。
6. **历史通过必须保留覆盖边界。** 11 月 10 日完整回归 2922 passed、32 项 Chrome 场景通过，都不包含上述新复现的完整条件。Linux 跳过浏览器测试也曾由独立 Chromium 镜像补验，不能把标准镜像的 skipped 当作 passed。

此前 Hook 审查重点是“不改草稿、不误 dirty、不阻止上传”；我没有覆盖“修改后保存再接旧响应”的顺序。这属于验收遗漏，本轮已明确记录，不能用原通过数量否认它。

## 四、可执行的预防方案

| 优先级 | 做法 | 验收标准 |
| --- | --- | --- |
| P1，先修已复现问题 | 修 F1，补真实默认 adapter 契约测试；修 F2 的统一输入失效和晚响应门槛 | 三个本轮失败探针转绿；原有下载、Hook、草稿和交付保护保持通过；不得放宽保存 CAS、文件校验或权限 |
| P1，每次异步/重试改动必做 | 为修改、保存、切换、重载、放弃、暂停、失败、未知回执建立交错矩阵；用 barrier/受控 Promise 确定时序 | 至少覆盖“发出后改动”“改动后保存”“回执丢失后显式重试”“另一窗口推进状态”；不靠 sleep 碰运气 |
| P1，共享模块集成门禁 | 对 webserver、workflow、material_versions、app.js、mosaic.js 的并行变更列出新增锁、等待点、调用方和对象所有权 | 合并后的候选跑 managed+legacy、已有队列、多账号/多项目混合场景；不是只重复各分支独立测试 |
| P1，跨版本恢复门禁 | 保留上一发布版本产生的任务/等待/草稿/结果夹具 | 新版本能合法接管等待；拒绝过期成功产物；保留 attempt/not_before/任务身份；坏记录不影响其他任务 |
| P2，明确状态职责 | 延续草稿、不可变确认版本、展示缓存、运行状态和交付回执的分离；给每个回写点定义谁有权写、写入前验证什么 | 后台展示结果不能写 draft；只有实际应用状态才提示同步成功；已确认版本不能被晚结果改写 |
| P2，锁与资源审查 | 维护实际锁顺序和阶段资源表，审查锁内 I/O、对象锁等待、取消后的 lease 转交 | 长媒体读/外网等待不新增到全局锁内；真实进程暂停/退出后资源回收；只读接口在调度锁占用时仍有界完成 |
| P2，性能优化等价性 | 对快照复用、finished-skip、分段重编码保留旧路径作为受控对照 | 同一业务输入在缓存开/关、优化开/关及异常/取消/重启下结果等价；媒体内容与时序校验不能为了性能被弱化 |
| P2，发布与证据 | 固定最终合并 SHA；清除默认 marker 过滤；Linux 浏览器补验单列；失败、修复、跳过、环境问题分别记录 | 发布镜像与被测应用哈希一致；测试代码仍只在验证容器/本地；覆盖结论按场景给出，不累加重叠测试数 |

不建议为了这次复盘立刻大规模重写。先把已确认缺陷和高频交界测试补齐，再在正常改动中逐步减少共享模块的状态职责。范围内 webserver.py 被 27 个产品提交触及，mosaic.js 26 次，app.js 18 次；这是集成审查应优先投入的位置，并非仅凭修改次数判断代码质量。

## 五、仍需排查，但不能列为已确认 bug 的部分

- 跨进程/重启恢复与交付幂等：已有线程级并发与 HTTP 验证不能替代所有跨进程崩溃窗口。重点检查未知远端回执、旧进程仍活着、已持久 outbox 未派发等边界；不能为了自愈自动重发外部交付。
- 长时间混合负载：单次双机/多账号验收证明所测场景，不证明无限负载公平性或所有超时边界。当前全局锁仍有小型文件/元数据操作，需用已有锁分段计时验证尾延迟。
- 快照缓存依赖遗漏：当前已有 stat/写入失效、worker 单轮作用域和 5 分钟全扫保护；将来新增恢复输入时仍可能漏进 fingerprint。需要对照全扫的属性/变异测试，不能仅依赖兜底扫描。
- 原片完整性：F1 修复后，还需验证合法 206 的范围、总长度及对象变化；尾帧校验不代表能发现所有中间损坏。这里没有复现生产错片，按风险补测。
- Hook 展示以行序号存储、部分操作改变行集合：本轮没有穷尽删除、重排与不同任务交错，建议纳入 F2 的 request_id/输入代际测试，而不是对每个事件再打零散补丁。

## 六、应从产品 bug 中分开的执行问题

11 月 10 日 Linux HTTP 浏览器测试首次失败，根因是验证容器继承 `EXACTCUT_WORKER_ENABLED=0`，使真实写入口返回 503；旧基线复现相同失败。修正隔离验证容器环境后通过，不能称作此次产品修复。

同日生产验收中，我把“不真实上传”的范围理解得过宽，同时浏览器拦截也没覆盖后端自动 OSS 上传，产生了 8 个测试对象，随后做了精确清理并记录偏差。用户已明确生产制作必须能上传 OSS。今后验收应分别写清 OSS 媒体存储与 FBBM/飞书业务交付的允许范围；保持生产 OSS 正常能力。这是验收执行和范围沟通问题，不把它虚构成生产上传代码缺陷。
