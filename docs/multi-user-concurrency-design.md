# 多用户任务并发与共享缓存设计

日期：2026-10-09。状态：设计讨论稿，已收到 Grok 审查并核对、补充关键协议；未实现、未启用并发。审查记录见 [Grok 审查与处理](multi-user-concurrency-grok-review.md)。本轮只修改文档，不调整本地或服务器配置；修订稿尚未再次取得 Grok 的通过结论。

> **文档状态（2026-10-09 晚更新）**：本文件是最初的设计讨论稿，保留供追溯。
> - **实施规范以 [并发改造计划](concurrency-refactor-plan.md) 和 [并发模型](multi-user-concurrency-model.md) 为准**；三者冲突时以计划为准。
> - **业务前提更正**：实际业务中多用户通常**不会剪同一部剧**，因此本文"共享下载归属 / 订阅集合 / 追随者"整套协议**后移**，不是并发上线的前提。
> - 容量：美东生产为 `cpus=14 / mem=24GiB`（见 [服务器规格](server-sizing.md)），与下文"容器 14 CPU、24 GiB"一致；东京旧共享机（1 核 / 2 GiB）仅作历史实测基线。

## 目标和边界

不同用户、不同项目的下载、制作和上传可并行。A 等待 FBBM 结果时，B 可以制作或上传。单个任务的失败、暂停和重试只影响其所属项目；共享提供商故障、账号限流和服务器容量不足仍可能影响多个用户。

用户项目指 `.web-state/batches/<batch_id>`，不是 `projects/<drama_id>`。后者是同一剧的公共素材与缓存目录。调度公平性按项目归属账号计算；管理员代操作时不改变项目的资源归属。

首期同一项目内制作、预览和上传操作依次执行，同一批次的多条素材也保持顺序制作。允许同一用户的不同项目分别制作和上传。正在发布的成片禁止覆盖；逐条确认和 SHA-256 核验保留。

## 已核实的现状

- `webserver.worker_tick` 在发现任意活动任务后停止启动新任务，每次只启动一个子进程。
- `batch_control.reconcile` 同样按全局串行逻辑恢复暂停任务。仅修改启动数量不能完整支持并发。
- `workflow._produce` 包含正片下载和制作；`workflow._publish` 包含上传、建立飞书记录以及循环查询 FBBM。
- 制作结果位于每个 batch 的 `production/`；发布状态位于每个 batch 的 `publications.json`。runtime 和发布记录有文件写锁，但这不等于同一 batch 的多执行器已经安全。
- 原始正片按剧号和集号共享，有下载独占锁和读取共享锁。基础剪辑、部分 Hook AI 缓存已经位于同剧公共目录。
- 本地/服务器当前仍是串行执行。服务器额度为容器 14 CPU、24 GiB，不能根据机器规格断言双任务性能已验收。

## 可以共享的内容

以下“已有”指代码支持相应复用，不代表已完成多用户并发压力验收。共享仅限同一实例及相同素材访问范围，不跨开发/生产数据根，不开放他人项目或缓存目录的直接浏览接口。

| 内容 | 当前代码情况 | 共享条件及收益 |
| --- | --- | --- |
| 剧集 MP4 和下载完成元数据 | 已有：`sources/<drama>/EPn.mp4` 及 `.json`；解析优先读取公共正片 | 同剧同集只下载一份；内容替换后下游缓存必须失效。元数据包含完成标记、大小、SHA-256 |
| 基础剪辑 MP4 | 已有：`projects/<drama>/cache/render-base` | 键包含处理后的时间线、正片 SHA-256、基础渲染配置和版本；复用剪切、标题卡与拼接，仍分别处理各自 Hook 和成片。时间线中的标题卡内容也必须一致 |
| Hook 文案的 AI 重点分析 | 已有：同剧 `cache/hook-emphasis` | 规范化文案、模型、提示词摘要及分析版本一致才能复用；人工选词仍使用本次请求自己的选项，不沿用他人选择 |
| AI 画面避让分析 | 已有：同剧 `cache/hook-placement` | 抽样图片字节、模型、提示词和当前缓存版本一致才能复用；这是画面区域分析，用户手动位置仍独立 |
| 正片时长及媒体信息 | 部分已有：`timing_review` 按文件身份缓存时长，限当前 Web 进程内存 | 建议增加按源文件内容和探测版本验证的持久缓存，复用时长、轨道、分辨率、帧率和探测结果，减少重复 ffprobe；当前下载元数据不含这些完整字段 |
| 剧集镜头索引 | 已有同剧文件：`projects/<drama>/data/episodes/EPn.video.json` | 可以共同读取，但现有文件不能据剧号就认定有效；需补源文件摘要、生成版本、并发写锁和原子发布后才能可靠并发生成 |
| 抽样帧和缩略图 | 当前主要在临时目录生成 | 后续可按正片摘要、时间点、尺寸、抽样算法版本缓存；可减少重复解码，首期不扩大到全剧抽帧 |
| 成片的低清预览、QC/安全检查的计算结果 | 当前主要在各 batch 内复用 | 后续可按最终成片摘要及完整生成/检查配置、版本共享计算结果；每个项目仍保存自己的检查证据和确认记录。首期保持现有隔离 |
| 字体、样式模板及同一访问范围内的剧目基础资料 | 字体与样式为应用资源；catalog 是实例级文件 | 共同读取即可；剧号有效的直接输入流程不应因 catalog 缺失而被禁止。用户自填信息不因共享剧目资料而覆盖 |

例如，A 和 B 都选 EP1 的 00:10–00:30 加 EP2 的 00:05–00:20，使用相同渲染参数：共享正片，也可共享基础剪辑；A 和 B 的 Hook 不同，则各自叠加 Hook、生成成片、检查并确认。如果选段不同，只共享相同正片及相关探测结果。

首期优先使用已有的正片、基础剪辑和 Hook AI 缓存，补齐并发保护。媒体探测持久缓存可以作为小范围后续优化；抽样帧、整条成片和跨项目 QC 缓存不作为并发上线前提。

## 必须独立的内容

- 项目草稿、确认版本、时间线、作者、结尾图片、人工 Hook 选项和反馈。
- 任务状态、下载进度的项目视图、错误、暂停/归档状态、重试记录与任务日志。
- 正式成片的项目归属和输出路径、逐条预览确认、批准上传的 SHA-256。
- 飞书记录与 FBBM 发布进度的项目映射。素材字节相同也不自动继承另一项目的发布成功或确认权限。
- 账号、会话和 AI 助手对话；不将带项目上下文的完整 AI 对话作为公共缓存。

共享基础剪辑不等于共享任务状态。A 归档或删除项目时，只清理 A 的产物，不直接删除公共正片或缓存；公共缓存由容量/保留策略清理，必须避开任何用户仍在读取或生成的文件。

## 调度方案

保留单个调度器和现有持久任务记录，每类任务使用有限并发子进程。暂不为单机引入 Redis/Celery。

| 工作类型 | 新服务器初始建议 | 每个用户初始上限 | 说明 |
| --- | --- | --- | --- |
| 正片实际下载 | 2 | 1 | 按剧集去重；依赖同一集的项目等待完成，不各启动一个阻塞下载进程 |
| 制作/成片预览 | 2 | 1 | 不同用户可同时制作；同一用户另一项目可同时上传 |
| OSS 上传和飞书入队 | 2 | 1 | 与制作分别计数，避免长上传阻塞另一用户的制作 |
| FBBM 单次查询/同步 | 2 | 1 | 只在执行一次外部调用期间占位置，等待下次查询时释放；必须按飞书记录防重复执行 |

上述数量为建议值，不是现有配置字段或已测容量。全局活动子进程上限建议 8，各池上限总和为 8；纯等待不计入活动数，但等待记录和常驻暂停进程也需有数量限制。默认配置保持全局上限 1，便于本地保守运行和兼容旧行为。线程/内存额度验收后再决定服务器是否需要降低某池数量。

调度采用用户轮转，同一用户内按提交顺序挑选可执行任务；被素材依赖、同项目互斥或缓存占用阻塞的任务不会挡住其他用户。首期不允许同一用户占满两个制作位置，即使另一个位置暂时空闲，行为和容量预算保持简单可预测。

现有全局排队阈值为 10。建议替换为可配置的全局待执行上限 64、每用户 8；内部素材依赖和定时查询不作为用户重复提交，但另设全局有界记录上限，避免绕过容量控制。这些同样是待实现的配置建议。

## 阶段拆分和共享缓存的并发保护

1. **下载与制作分开准入。** 确认制作时按 `confirmed.json` 的真实需求准备正片，复用预下载机制；编辑期接口仍只处理草稿。扩展内部下载执行器，使确认后的正片准备不会被现有“仅 draft”判断跳过。素材全部到齐并校验后才进入制作池。制作启动时若源文件缺失或变化，返回准备阶段，不能在制作位置内悄悄进行长下载。
2. **上传与等待分开。** 上传并保存已建立的飞书记录后退出上传执行器。调度器按既有 `publish.poll_seconds` 安排单次 `sync_record_once`，保留超时及失败后的继续查询行为；`quota_deferred` 按现有返回含义延后。查询可能创建素材或触发重同步，并非纯 GET，因此同一外部记录必须互斥。
3. **同 batch 执行互斥。** 下载准备结束后才能开始制作；制作结束且通过确认后才能上传。FBBM 等待期间可继续展示和编辑下一项目，但首期禁止重做正在发布的同一项目。对同项目不同发布条目也依次安排，避免覆盖公共 runtime。
4. **同源实际下载去重。** 不同 batch 依赖同一集时只允许一个实际传输；追随者拥有各自等待/错误状态，读取同一传输结果。已有文件锁保留作为最终正确性保护，调度准入需避免让多个工作位置全阻塞在同一文件锁上。
5. **公共计算只由一个写者生成。** 正片、基础剪辑和 AI 缓存继续用键级锁、完整验证、临时文件与原子发布。基础剪辑当前锁覆盖 Hook 阶段；应缩小独占生成范围，并在后续读取期间使用共享锁保护，避免不同 Hook 无谓串行。遇到未就绪缓存返回等待调度；不能无限阻塞工作位置，暂停持锁进程也需在准入时识别。
6. **容量同时预留。** 现有下载和渲染空间检查不能扣除其他任务即将写入的空间。新增统一、可恢复的在途预留，分别覆盖源目录、输出和临时文件所在文件系统；下载逐集预留。任务失败/结束释放，暂停保留，恢复时根据真实进程及文件重建，不双重计算已落盘内容。
7. **命名与外部写入保护。** 保留全局素材序号分配锁。现有 OSS 是先查存在再上传，飞书是先搜索再创建；并发时需按目标对象/记录加实例内互斥，避免检查后竞态。不能因 MP4 相同合并不同用户的发布操作；现有业务命名和 OSS_URL 查重约定保留，并显式检测碰撞。跨实例或外部工具同时写的幂等保证不能仅靠本机锁宣称成立。

## 共享工作归属与取消规则

以下是拟新增的内部操作协议，不是现有 API 的字段或已实现行为。

- 实际下载按实例、剧号、集号建立唯一共享工作，独立于任何 batch 的 `children`。各 batch 保存自己的依赖关系、进度视图和错误；调度器维护共享工作与订阅集合。共享工作仍遵循本实例进程令牌和接管规则，不作为未经审计的旧 project 命令处理。
- 下载准入按仍有需求的最早订阅账号计额度，全局只计一次。该账号离开后，将公平调度归属转给仍有需求的最早账号；变更不重启实际传输，也不改变其他用户的队列位置。其他订阅者等待同一结果，不启动阻塞文件锁的第二个下载进程。
- 暂停、归档、取消或删除项目，只移除该项目的活动订阅，不向共享进程发 `SIGSTOP` 或直接删除其日志。其他项目仍需这集时继续传输；暂停项目的需求可保留为非活动订阅，继续时重新挂接工作或复用完整缓存。
- 无活动订阅且尚未启动则取消共享工作；已启动则由调度器核验身份后发送 `SIGTERM`，等待退出、清理临时文件及释放预留后才允许同键再次启动。现有 finally 不能保证强制退出或机器断电后的临时文件自动消失；恢复时在取得独占锁并确认无活写者后清理遗留文件。
- 失败向各依赖项目分别投影，仅同源依赖共享这次失败。重试先核对同键存活写者，禁止重复启动。进度读取实例级共享工作，再按各项目真实所需集数汇总，不再只查询本 batch 的 prefetch job。
- 文件已完成时先在共享读锁内校验并复用；现有 `_ensure_one` 即使缓存命中也先拿独占锁，需调整，避免正在读同一集的制作任务阻塞另一个用户的缓存命中检查。
- 基础剪辑生成也按缓存键成为共享工作，负责生成和发布可验证的基底。Hook 叠加仍为 batch 私有工作。共享基底写者不被某个用户的暂停冻结，订阅、取消、错误及接管采用相同原则；制作池同时限制共享基底生成和私有 Hook/QC 工作的数量，不额外无限增开编码进程。

## 缓存发布、锁与暂停协议

- 基底只在身份、文件 SHA-256 和现有时长容差均通过时算命中；读者必须在共享锁内核验。仅 MP4 存在而 metadata 未完成不算可用，由唯一独占写者重新校验或生成。
- 独占生成锁只覆盖检查、生成、文件替换和 metadata 发布，AI 许可等待、Hook 叠加不在此范围。读者拿不到非阻塞锁则返回依赖等待，不占工作位置。独占锁转共享锁期间若存在释放窗口，重新取得共享锁后再次校验文件和 metadata，不能假定两者未变化。
- 共享读锁覆盖读取基底、正片及源摘要所对应的完整使用期；不能在源摘要读取后、实际渲染前允许另一个写者更换正片。读取期间更新使用时间；清理仍以非阻塞独占锁为准。缓存键应包含影响结果的管线版本，代码或字体导致基底生成规则变化时明确失效。
- 共享下载/基底生成的写者不响应单个 batch 的暂停信号。私有制作的暂停改为安全点握手：收到暂停请求后，子进程在未持有 runtime/publication 写锁、共享独占锁或 AI 许可的安全点自行停止进程组，持久确认后才显示已暂停。父进程不能先猜测锁已释放再异步 `SIGSTOP`，否则仍有竞争窗口。
- 已接受请求但尚未到安全点时显示正在暂停；当前不可中断的媒体阶段可以先结束。继续恢复只针对核验过身份且已确认停止的进程，按同类资源容量及用户轮转安排。保留只读锁可防回收，但不应阻止其他读者；存储预留与内存占用仍保留。
- Web、控制、调度与预留账本锁只做短时状态事务，不在持锁期间等待媒体计算、网络或缓存锁。禁止缓存写者反向等待父进程持有的调度锁。公共写工作、私有工作、暂停和收尾的锁顺序及故障窗口必须分别有回归。

## 阶段结果、发布等待和幂等边界

进程终止与业务完成分开判断。拟新增内部阶段结果包括：完成、等待依赖/资源、等待 FBBM、失败、外部结果待核实；这些不是外部提供商枚举。短任务退出码为 0 只说明当前阶段成功，调度器依据持久结果推进下一阶段，不能直接套用现有 `finish_job` 的批次收尾规则。

| 持久业务情况 | 下一步 | 是否占活动位置 |
| --- | --- | --- |
| 所需正片未完成 | 订阅共享准备工作；完成后校验并安排制作 | 仅实际写者占下载位置 |
| 制作或预览完成 | 保存本 batch 的结果并进入可预览/确认状态 | 退出执行器后释放 |
| 上传和入队完成，已保存本条飞书记录 ID | 保持本条 `fbbm_queued`，安排单次查询；整批仍可处于 publishing | 两次查询之间不占 |
| 查询 action 为 ready 且有 video_id | 本条进入 `fbbm_ready`，按全部条目汇总批次状态 | 查询退出后释放 |
| 查询 action 为 syncing 或 resync_requested | 保持 `fbbm_queued`，等待下一次查询 | 等待不占 |
| 查询 status 为 quota_deferred | 保持等待，按现有 10 分钟额度退让语义延后 | 等待不占 |
| 查询 action 为 failed 或本地等待超时 | 本条失败，保留原记录供用户继续查询 | 不占 |
| 外部写入可能成功但本地没有可核对结果 | 保留待核实状态，恢复先核对外部结果 | 不盲目重放写入 |

- 更新 `finish_job`、`recover_jobs`、`execution` 及批次状态汇总：无进程的 FBBM 等待是正常状态，不视为 interrupted/publish_failed。单次查询不重复清空整批制作的 stage 和 active_request。每次 tick 收割全部新建和接管进程，不能仅在 `owned` 为空时检查；阶段结果按 job 校验，不能按一个 batch 是否还有活进程跳过其他 job。
- 上传前先持久化本条发布意图，包括由既有 `key_for` 得到的对象目标和已批准 SHA-256，并绑定 batch/request。确认时的全局命名锁和目标对象互斥保留。对象已存在且与本条发布意图一致时允许核验并恢复自己的操作；不能简单因本地缺飞书 ID 就拒绝所有已有对象，否则会破坏上传后的崩溃恢复。
- 飞书恢复只使用已验证的 OSS_URL 搜索契约及实际返回列表：零条才允许继续建立记录，唯一匹配且与本条发布意图一致才绑定，多条或归属不明继续待核实。当前 `search_by_url` 只返回首条，必须在实现时补多匹配检测，不猜新增外部幂等 API。
- 查询可能触发 ingest/resync。调用前持久记录操作意图，调用后尽快保存结果；写入成功但结果丢失时，先读取已知记录核对。若平台没有已验证的查重/幂等依据，就停留待核实，不能自动发起第二次不确定写入。远端平台故障和限流仍是共享约束。
- FBBM 截止时间持久化为墙上时钟时间；暂停时保存剩余等待预算、停止新本地查询，继续时重建截止时间并先查远端现状。已经发出的远程请求及平台处理不会被本地暂停撤回；其结果先安全保存，再暂停后续调度。截止时间不能因为 Web 重启无条件重置。
- 发布升级仍先收敛旧任务。恢复如果发现旧版单体 publish 执行器仍活着，按上传/查询资源保守计占用，并禁止对它的同一飞书记录另开单次查询，直至原进程结束。

## 磁盘账本与总量限制

- 预留归实际写工作：同集下载、同键基底各记一次；私有 Hook、成片、预览记各自额度，不能因为基底共享就免掉私有输出预算。
- 按文件系统 `st_dev` 归并源目录、输出目录和临时目录，同盘统计一次可用空间。扣减的是其他工作预计尚需写入的空间；每项预算须覆盖中间文件和最终文件同时存在的峰值。
- 对已确认属于本工作、仍占用磁盘的完整/临时文件，剩余额度为 `max(0, 峰值预算 - 已落盘计入量)`。临时文件被删除时及时恢复相应额度。超出估计前申请增加预算，未获准则停止新写入。来源不明的残留不能用来虚减额度。
- 启动前先持久化准入及预留，再创建带令牌的进程。恢复先按令牌找齐启动窗口内的写者，再核对其文件及额度；进程结束后残留仍计实际占用，待安全清理，不同时保留无主预留。运行或暂停的写者保留剩余额度，不能因原 batch 删除就释放仍服务其他订阅者的预留。
- 缺少并发配置时全局活动上限仍为 1；数值类型、范围或组合非法时按既有配置验证习惯阻止启动并明确报错，不静默采用服务器建议的 2，也不静默忽略错误回退。
- 常驻暂停进程初始上限建议 2；制作常驻进程总量初始上限建议 2（活动加暂停），还须满足总内存预留。暂停只释放 CPU 活动额度，并不凭空释放内存额度。达上限时拒绝新暂停并让原任务继续执行。
- 活跃、排队、暂停及归档后仍待继续的用户工作都计入其未完成工作上限，防止通过暂停/归档绕过每用户 8 的限制。共享依赖和周期查询另以每个共享键/发布条目最多一条待调度记录计数，初始全局共享工作上限建议 64；已接受的 FBBM 等待直接复用条目上的下一查询时间，不每轮追加 job。
- owner 读取既有 `accounts.owner(batch_folder)`，即 `access.json` 的 owner，旧项目按既有 admin 回退。`actor` 仅用于审计。实例身份沿用 `runtime.instance_marker` 对绝对数据根的 SHA-256，重启及切换代码版本保持同数据根时不变；搬迁期间先收敛进程，不跨机器继承活进程 PID。
- AI 初始实例级调用上限建议 2，覆盖 Hook、预览、助手及其他现有 AI 入口。纯缓存命中不占调用许可；未拿到许可的后台阶段返回资源等待并释放制作位置，Web 请求按现有繁忙响应习惯返回可重试结果。调用超时/429 做有界退让，不能持缓存独占锁等待许可；许可须关联进程身份，接管后重建、退出后释放。

这些内部协议确定后，编码阶段的初始额度仍需双任务实测。全局活动上限 1 指同时最多一个工作子进程；A 在无进程的 FBBM 等待期间允许 B 制作，是本次明确要改变的行为，不承诺复现旧版全机等待。

## 资源、暂停和恢复

- FFmpeg 当前未统一限制线程。需覆盖切片、拼接、Hook、预览和检查命令；服务器先以编码线程 6、解码线程 2、滤镜线程 1 作为待测起点。线程数不是单任务硬 CPU 配额，容器总额度继续兜底；保留画质、preset 和 QC 阈值。
- Web Hook 预览、时间探测及 AI 助手有各自限流，应计入 CPU/内存和提供商总调用预算；子进程内的独立信号量不能被当作实例级 AI 限额。
- `SIGSTOP` 暂停会保留内存、只读锁和磁盘预留；按前述安全点握手执行，不在共享写锁内暂停。恢复必须走同一调度容量检查；设置常驻暂停进程数量上限。上限到达时拒绝新的常驻暂停并保留原执行状态，不能暗中丢弃暂停任务。
- 重启后沿用 PID/进程组/启动令牌/实例身份校验，先接管全部存活执行器并重建各池占用，再启动新工作。恢复代码不能继续把“一个 batch 活着”视为全局唯一运行者。
- FBBM 等待记录保存下一查询时间和截止时间等可选操作状态，明确运行等待和用户暂停的时间语义；继续查询原记录不得重新上传。外部写已成功、本地记录未保存的崩溃窗口必须测试；缺乏外部幂等依据时保留待核实状态，不能无依据承诺恰好执行一次。
- 每条调度日志带任务、batch、所属用户、阶段和等待原因，记录排队/执行耗时及缓存命中；不记录凭据、对话正文或完整提供商敏感响应。

## 验收与回退

必须验证：A 长时间等待 FBBM 时 B 能制作/上传；两用户制作同时存活；一个用户的连续提交不挡其他用户；同剧同集一次传输；同基础剪辑一次生成、不同 Hook 独立成片；一个用户暂停/删除不损坏另一个的共享读取；两任务同时申请空间不越过预留；重启不重复启动/上传；旧任务、空 catalog 和默认串行配置继续可用。

审查后追加：三用户同集，最初发起者暂停/取消/删除后其他订阅者继续；最后订阅者离开后正确终止并清理共享写者；有 MP4 无合法 meta 不命中；安全点暂停不持 runtime/共享独占锁；接管进程退出时其他新进程仍在运行也能收割；上传正常退出及 quota_deferred 不变失败；外部写成功、本地结果未保存时进入可核实恢复；命名碰撞不绑定另一用户记录；同盘、多目录及写入过半重启时预留不双计；暂停/归档不绕过用户上限；全部 AI 入口共用额度；旧版单体发布执行器与新查询不重叠。

记录两任务总完成时间、各自排队与阶段耗时、CPU、峰值内存、线程/进程数、磁盘与网络吞吐；当前 `pids_limit=256` 需验证。并行可能降低单条编码速度，应以整体吞吐和用户等待衡量，不能承诺每条耗时不变或固定达成率。

持久 schema 保持 1，新增调度操作字段须可选并兼容旧记录。回退前进入维护、停止新准入，收敛活动/暂停子进程及未完成 FBBM 等待；旧代码不认识新的查询任务，因此不能直接带活动等待任务回退。将待查询状态转换为旧代码可继续原记录的状态并测试后再切版本，不恢复旧账号库或删除用户数据。调低并发也先收敛已有任务，不能即时杀掉工作来满足新额度。
