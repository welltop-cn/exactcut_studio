# 成片并发确认上传与剪切打码冲突处理设计

状态：方案已完成两轮自审，尚未实现；编辑队列最终接口与集成验收为实施依赖。依据当前代码 `3f2ef04`、本轮隔离复现与用户明确要求。

关联：[上传调研](../../design/upload-submission-concurrency-research.md)、[剪切打码后台队列设计](剪切打码后台队列设计.md)、[素材生命周期](../../material-media-lifecycle-design.md)。

## 1. 用户需求与本次决策

用户可在素材 A/B/C 上连续点击“确认上传 FBBM”，请求直接并发发送。后端负责原子防重复、持久化及调度；前端不要求等待上一条响应、上传或平台处理完成。

后台复用现有 upload 队列，初始上传池上限为 1；poll 独立。一次上传执行到 OSS 上传并创建/复用飞书记录后释放槽位，不等待 FBBM 最终就绪。外部飞书自动化仍管理 FBBM 同步，本方案不声称将外部自动化串行化。

如果同一素材存在会改变成片或仍可应用修改的活动，必须先经过第 14 节统一活动检查。其中剪切打码任务排队、运行、取消中或未确认的处理结果，服务端返回明确冲突，界面允许：

- **暂不上传**：本次不入队，原剪切打码任务继续。
- **取消剪切／打码，上传当前成片**：明确放弃本次修改的应用，后台停止任务，确认它不再具有替换权限、当前成片未变后，上传用户已经预览确认的原当前成片。

不直接删除锁文件、不因为写入 cancel_requested 就立即上传，不自动把刚生成的新片当成用户确认过的片子。

本轮仅设计，不修改生产配置或业务代码。

| `material_versions.py:_queue_delivery` | 已校验当前 version、SHA、项目控制状态、交付阻塞、文件名冲突，并同文件落盘 delivery/outbox。复用这些约束。 |
| `material_workers.py:recover_outbox` | 已有确定性 upload job、恢复和外部意图保护，不另建上传执行器。 |

| `cutting_access.py:require_editable` | 已有交付锁定规则，新的上传等待意图也必须纳入这里及制作/删除等冲突入口。 |

当前上传入队只通过短时 gate；生成线程并不全程持有素材 gate。因此冲突判断必须查询权威编辑任务状态，不能仅凭“这次拿到了锁”推断没有剪切打码任务。

## 3. 上传请求契约

保留 `POST /api/batches/{id}/publish`，正常请求继续使用已存在的 `request_id`、`version_id`、`sha256`、`submission_token`。旧调用携带的 revision 可以接收，但不作为上传准入条件；其他写入不变。

以下字段是**本方案拟新增契约**，并非现有接口事实：

- `approval_generation`：拟新增的素材级上传确认轮次，来源于服务端详情。只在同一成片的上传意图被撤销或终止时推进，不随其他素材或后台状态变化。用于拦截撤销后迟到、尚未被服务端见过的旧请求；见第 15 节。
- `retry_of_delivery_id`：只在用户明确重试一条已确定可重传的失败交付时传入；普通点击不传。
- `edit_resolution`：只允许 `cancel_and_publish`，表示用户明确选择停止编辑后上传已确认的当前成片。
- `edit_conflict_token`：服务端返回、绑定项目/素材/源版本及冲突任务集合的校验值。集合必须覆盖第 14 节中的关联编辑活动，不能只取最新 session。它是并发前置条件，不代替权限认证。任务集合或源版本变化后需重新展示冲突，不能取消后来出现的新任务。

成功响应保留现有项目详情与 mutation。新增 `upload_submission`，只包含以下已定义字段：

| 字段 | 含义 |
|---|---|
| `id` | 持久上传请求 ID，由服务端生成 |
| `status` | `waiting_edit_stop`、`queued`、`blocked`、`cancelled`；queued 表示已交给现有 delivery，后续阶段读取该 delivery |
| `delivery_id` | 尚未创建交付时为 null，入队后绑定唯一 delivery |
| `reused` | 本次请求复用了已经存在的业务请求，未创建新任务 |
| `reason_code`、`message` | 被阻塞/终止的稳定原因和用户可读说明；无原因时为 null |

新建或已有未完成请求均返回 202；已完成交付的重复请求返回 200 并展示已有交付。固定幂等回执与最新任务状态分开：mutation 保留原回执，upload_submission/项目详情返回最新状态。

冲突返回结构化 409：`code=asset_edit_conflict`，包含 `edit_conflict_token` 与 `edit_conflict`。后者只有服务端实际核实的任务 ID、种类（剪切/打码/混合）、阶段、源版本，以及 `can_cancel`。无可靠任务归属的文件锁冲突不能伪装成可取消的剪切任务。

成片变化使用 `code=asset_version_changed`；不能取消的短暂提交阶段使用 `code=asset_edit_committing`；幂等键载荷冲突、暂停/归档、待核实分别提供稳定错误码，不依赖中文字符串判断重试。

## 4. 防重复与失败重试

两层防重均在服务端：

1. **请求幂等**：同 submission_token、同标准化语义载荷返回同一请求。digest 包含素材/版本/SHA、approval_generation、明确重试对象、冲突处理选择和冲突 token；不包含项目 revision。相同键换素材、换 SHA 或换选择必须拒绝。
2. **业务防重**：不同窗口、不同 token 对同项目/素材/版本/SHA/交付目标的普通确认复用既有有效请求或交付。pending/upload_queued/uploading/fbbm_queued/fbbm_ready 均不新建；unverified 返回待核实，不重新上传。不同目标也不能绕过同素材旧交付的阻塞，目标变化要求核实原记录。

仅返回已有任务属于查询，不再次执行外部副作用；权限必须重新检查。已经接受后项目暂停或成片随后变化，原 token 重放仍返回原回执和最新状态，不把它当作新审批。

明确失败重试必须指定 `retry_of_delivery_id`，服务端检查该交付属于此素材、已结束且无存活执行器，并有明确的“尚未提交飞书”证据。可复用已存在 OSS 对象，不把 OSS 存在当作重复平台素材。

只有 publish_failed 标签不足以授权重新上传。存在 publication、外部 receipt、核实历史或结果未知时，保留原记录，走现有查询/核实路径；本次不增加自动重新发布能力。

新尝试在记录中保存 retry_of_delivery_id；针对同一失败父记录的两个并发重试只产生一个后继。后继也失败后，必须针对后继再次明确重试，旧页面的延迟请求不能创建第三次交付。

旧 mutation 没有新版 digest 标记时先按旧完整载荷摘要匹配原回执。旧页面 revision 改变造成 token 改变时，由业务防重兜底。新增字段保持 schema_version=1 的兼容扩展，不能重写历史摘要假装兼容。

## 5. 原子准入与锁

上传入口集中承担校验、幂等、防重、冲突识别、持久化，不让前端拼接多次“先取消、再解锁、再入队”的请求。

正常准入：鉴权 → 读取/复用已有请求 → 获取编辑 gate → 校验文件及身份 → 项目短事务内再次读取权威状态、判重并检查当前版本/控制/编辑任务 → 同文件写入请求、delivery、outbox、幂等回执 → 返回接受结果。

文件哈希、网络调用、复制大文件不得放在项目状态锁内。最终事务仍需重新核对版本/文件绑定，避免校验完成后成片被替换。

建议为 `cutting_access.gate` 增加只对上传确认使用的素材共享读模式：两个上传确认可以同时保护同一不可变成片，最终由项目状态锁串行去重；替换/剪切提交继续持有排他模式。默认模式不变，禁止把所有 gate 全局改成共享锁。

统一锁序：编辑 gate → 项目 media lock；不得在 media lock 内等待长任务、进程退出或持有任务状态锁调用回来。编辑队列状态和父上传意图需要一起决策的入口遵循该顺序；执行器更新其任务文件后释放任务锁，再进入协调入口。第 14 节的活动注册与上传占位必须使用同一事务裁决范围，不能扫描完任务文件后无条件放行。

取消、执行器退出回报、结果失效处理使用绑定 upload_request ID 与 task ID 的内部路径。此路径只允许推进已授权任务至停止/失效，不调用会被自身 waiting_edit_stop 挡住的通用 require_editable；不允许借此启动新任务或替换成片。状态查询和停止请求的 HTTP 路径也要避免被自己新增的上传冻结反向拦住。

新的等待取消请求会冻结该素材的新剪切打码提交、确认替换、删除、重新制作和其他会改变确认对象的操作。读状态/播放可用；其他素材不受影响。各入口必须读持久请求状态，而非只检查某个 Python 进程里的集合。

## 6. 编辑冲突对话框

常规上传冲突时不创建 delivery，不提前通知“已入队”。

**标题：这条素材正在剪切／打码**

**正文：本次修改尚未应用到当前成片。你可以继续处理并暂不上传，也可以停止本次处理，上传之前已预览的当前成片。**

按钮：

- `暂不上传`（默认焦点，关闭/ESC 同义）：不取消编辑，不记录上传意图。
- `取消剪切／打码并上传当前成片`：提交带冲突 token 的显式选择，成功持久化后显示“正在停止剪切／打码，停止后上传当前成片”。

状态细分：

| 编辑状态 | 行为 |
|---|---|
| 排队 | 从可调度集合取消，确认不会被领取，再交付当前成片 |
| 运行/取消中 | 持久取消请求，等执行器及所属子进程退出；取消中重复点击复用同一请求 |
| 生成完成待确认 | 文案改为“放弃未应用结果并上传当前成片”；保留参数和文件，撤销该结果的确认替换资格 |
| 替换准备中 | 新增可取消检查点；停止准备并等待 gate 释放，当前版本未变才继续 |
| 原子提交已开始或刚完成 | 不强行取消/回滚。等待确认提交结果；版本变化则结束本次上传，显示“成片已更新，请预览后重新确认上传” |
| 仅打开编辑器、无最终任务/待确认结果 | 不视作正在剪切任务；正常上传后编辑端按已有交付保护转为不可提交 |
| 无法识别的占用或无取消权限 | 明确提示暂时无法取消，不展示可执行的强制解锁按钮 |

当前渲染阶段“完成”但未确认替换，不等于当前成片已经变化。取消选择表示不应用此结果，而非删除既有媒体。

## 7. 后台取消后上传的持久交接

为实现关闭页面后继续，父 `media-state.json` 增加可选 `upload_requests` 字典；旧文件缺省为空，不迁移 schema。

每条请求记录服务端 ID、认证 actor、素材/版本/SHA、目标指纹、幂等请求标识、明确重试对象（如有）、已授权取消的任务引用/冲突 token、状态、delivery_id、时间和可展示错误。任务引用取自权威队列，不接受客户端指定任意进程/PID。

用户确认取消时，在短事务内验证冲突集合未变并写入 waiting_edit_stop；这就是本次“后台处理请求已接收”的持久化界点，同时冻结该素材。

协调器通过以下阶段完成交接：

1. 找到 waiting_edit_stop，幂等请求对应编辑任务取消；取消对象固定，不能追着后来任务无限取消。
2. 编辑队列完成真正停止并撤销结果应用资格；停止/失败保留原成片和参数。
3. 协调器核实无活动执行器、无后续替换资格，取得 gate 并复核成片版本/SHA、项目状态、权限、目标指纹。
4. 在同一父状态事务中创建唯一 delivery/outbox，绑定 upload_request.delivery_id 并改为 queued。
5. 既有 outbox 恢复器生成上传任务。

取消请求尚未写入编辑队列时崩溃：父请求仍在，恢复重复请求取消。编辑已停止但尚未入队时崩溃：恢复核验后入队。入队后丢响应：请求与 delivery 绑定已落盘，返回同一条。严禁跨文件状态“先删锁、再写 delivery”。

停止失败、源版本改变、权限撤销或目标改变 → blocked，记录具体原因，不自动上传。blocked/cancelled 是本次上传请求终态；只有新的明确确认才能产生新请求。项目暂停/归档时，尚未生成 delivery 的等待请求也转 blocked，不因恢复项目自动重新上传；已存在 delivery 的暂停恢复仍沿用既有规则。已受理的取消动作可以完成。上传请求终止不意味着编辑任务已经停止，冻结释放规则见第 15 节。

waiting_edit_stop 支持明确撤销“后续上传”：状态 cancelled 后不创建 delivery；已经发出的取消不承诺撤回或自动重启编辑。与入队竞态由同一事务裁决；如果已经 queued，告知已进入上传队列，不能假装撤销外部提交。

## 8. 与剪切打码队列的衔接

复用那份设计的权威 queued/running/cancelling/completed-awaiting-confirm 状态与取消机制，不另造一个剪切任务注册表。需由其实现提供三项内部能力：查询素材的冲突任务及提交阶段、幂等请求取消指定任务、验证任务已停止且结果失去替换资格。

这些是本设计要求的内部接口语义，不预设尚未落地的函数名和 JSON 字段。集成时以其最终提交中的真实契约映射，并补充契约测试；不能用推测字段适配。当前旧剪切入口同样必须纳入查询和取消，不能绕开保护。

替换准备中新增合作取消和提交前原子取消检查；提交不可分割区间不接受“已取消”承诺。先赢得原子裁决的一方决定结果：取消赢则旧片保留；提交赢则当前版本改变，本次旧 SHA 上传请求 blocked。

业务版本/任务集合不明，或旧任务缺少可验证执行身份时，只能提示无法安全取消；不能按名称搜索并杀任意 FFmpeg。

## 9. 前端并发和恢复

按 `(batch_id, request_id, version_id, sha256, approval_generation, retry_of_delivery_id)` 管理提交状态，不用 DOM 元素或列表 index 作为任务身份。不同素材各自立即发请求；同一素材提交中只禁用该素材按钮。

初次请求及网络不明重放保持同一个 token 和固定载荷；sessionStorage 键不包含项目 revision。用户改变“是否取消编辑”是新的明确意图，用新的 token；失败重试也必须携带明确的原交付 ID。

状态文案依次为：提交中 →（需要用户选择／正在停止修改）→ 等待上传 → 上传中 → 平台处理中 → 已完成。网络超时显示“提交结果待确认”，先查服务端请求/交付状态，仍不明可用原 token 重放；不显示普通失败后自动换 token 重传。

响应按项目身份、版本单调性及素材身份合并。较旧整份项目响应不得覆盖较新状态；即使响应详情过时，本次接受回执仍可单独确认并触发刷新。切项目后的结果只更新对应缓存/请求状态，不替换当前页面。

轮询持续更新其他素材，不因一条素材 busy 阻止整个项目刷新；保留本地未保存草稿及其严格保存基线。每条素材的失败/冲突独立显示，不用全项目“制作失败”代替上传提交问题。

页面刷新/重开后从服务端 upload_requests 投影和已有 deliveries 恢复。服务端持久接受前关闭页面，不能保证请求已提交；接受后取消等待与上传都不依赖页面继续运行。

## 10. 调度与资源

复用 `material_workers` + `webserver` 的持久 jobs、owner 公平调度及 upload/poll 分池。

初始设置 production 配置中的 upload=1。注意 `media-upload` 补传也映射 upload lane，会共享这个上限；不新增第二套互不知情的上传容量。poll 保持原配置。跨用户公平，不承诺全站严格 FIFO 或准确的等待名次。

等待用户选择、等待编辑停止、completed-awaiting-confirm 均不占 upload 槽位。一条失败/待核实不得阻止其他素材上传。

配置上线后先确认有效配置和在途任务：降低容量只限制新准入，不强杀已经运行的两个上传。

## 11. 文件分工

| 文件 | 工作 |
|---|---|

| 替换竞争 | 取消先提交则旧片上传；替换先提交则旧确认 blocked；不回滚新成片、不直接删锁 |
| 其他人/新任务 | 未授权不能取消；冲突 token 过时不取消新任务；其他素材任务不受影响 |
| 撤销等待上传 | 不撤回已发取消；与入队裁决一致；页面不能声称已取消已开始的上传 |
| 崩溃恢复 | 等待意图、取消请求、停止完成、交付提交每个断点注入重启，无漏单/重复外部写入 |

| UI 并发 | 响应倒序、切项目、DOM 重建、轮询与未保存草稿不串素材、不回退状态 |

### 14.3 统一检查必须防止“检查后又启动”的竞态

1. 以项目 + 素材 ID 查权威候选、全部编辑 session/新队列、upload_requests、deliveries/outbox 与内部 child lineage；包括 queued、running、waiting_resource、cancelling、完成待确认和未知执行身份。仅看前端 busy、runtime 聚合状态、文件存在或一把锁都不够。
2. 长 IO 前做预检；最终准入事务内再次核验。检查范围对 request-less 批次写任务保守扩大到批次，对明确属于其他素材的任务放行。
3. 上传等待意图或 delivery 创建的同一事务建立素材占位。所有冲突入口（包括确认制作、候选提交、自动恢复、旧剪切入口、识别/跟踪/片段预览、确认替换）同样受占位约束，两个操作只能有一个先成功。共享上传读 gate 不可代替这个事务。
4. 活动候选存在则上传不准入；上传占位存在则不能再创建/恢复该素材的新候选。整项目 confirm 保持原有事务语义：实际要新制作的素材中若有冲突，整次拒绝并明确列出素材；已经完成且本次本来会跳过的素材不因正在上传而阻止其他素材制作。不新增部分成功/自动跳过冲突素材的协议。已经在占位之前存在的候选必须先结束并解决冲突，不能由上传操作静默丢弃。
5. 编辑最终提交入口与这些短编辑活动采用同一 gate 及权威注册协议。状态文件读不到、任务身份/进程归属不明、孤儿活动仍有写能力时明确阻止，不能把异常当作空任务集合。
6. 用户取消覆盖提示时实际显示的任务集合。关联任务必须先登记后启动，派生任务继承取消/失效标识；waiting_edit_stop 建立后不能再追加未授权的新活动。对取消中仍持锁的任务等待其实际结束。
7. 停止完成后，在转为 delivery 的同一原子决策中重新检查活动集合和 version/SHA；不存在“解锁后再发一个上传请求”的空隙。
8. 正式上传执行前复核交付固定快照和完整性。已经合法接受的 delivery 不随其他素材状态变化而失败；如发现应当已被围栏阻止的同素材活动，停止并记录矛盾证据，不猜哪份文件才对。
9. 旧版已存在“候选与 delivery 共存”的数据升级时应识别并报告，保留原 delivery/回执；不能自动取消已提交平台的交付，不能自动切换交付版本。按实际活动与执行证据处理，禁止批量清空状态。

| waiting_edit_stop | 仅所有授权任务安全结束且条件仍满足时 | 保持 | 继续取消，禁止新任务/替换 |
| queued（已有 delivery） | 已完成转交 | 由 delivery 状态负责 | 旧任务必须已失效 |
| blocked | 永不自动恢复；新明确确认才可再申请 | 释放本请求的上传占位 | 仍运行/取消中的编辑保留自己的活动保护 |
| cancelled | 永不自动恢复 | 释放本请求的上传占位 | 已发出的取消继续完成，不自动重启 |

不能把 upload_request 终止等同于任务全停，也不能为了保守永久锁住素材。发生不可判断的执行状态时由该活动的 unknown 状态阻止修改，不靠一个失效上传请求维持锁。

waiting_edit_stop 的协调不在 HTTP 或总调度 tick 内长等。逐次执行短步骤，持久化最后进展、原因和受限重试时间。采用集中配置 `material_lifecycle.upload_cancel_wait_seconds`（拟新增，默认 120 秒）作为自动交接期限；超过期限转 blocked，告诉用户停止尚未完成、本次不会自动上传，保留真实取消和活动保护。该期限不是杀进程或强制解锁期限。

恢复协调不能每 0.5 秒全量哈希所有等待文件；状态未满足时只做轻量检查，满足转交条件时才校验大文件。相同错误限频记录。

### 15.3 撤销后的迟到请求：素材级确认轮次

仅靠 token 防重不能阻止一个从未到达服务端的旧请求在用户撤销后首次到达。拟在 asset 增加 `upload_approval_generation`（旧记录默认 0），详情投影为 `approval_generation`。

- 普通确认携带页面取得的轮次，属于请求 digest 的一部分。
- 本次请求原子转 cancelled/blocked 时推进该素材轮次；重复终态处理不重复推进。
- 服务端先查已存在 token 的原回执，再校验新准入轮次；轮次过期的新请求拒绝并要求刷新确认，不创建新任务。
- 查询、worker 状态更新、其他素材提交都不推进它。它不是项目 revision 的改名，不能重新造成 A 入队挡住 B。
- 同一轮次多个 token 仍用业务防重合并。已有交付不因轮次变化被再创建；明确失败重试仍由 retry_of_delivery_id 的单后继关系约束。
- 前端重新确认前拉取当前身份；按钮勾选绑定 version/SHA/轮次，源身份变化必须清除，不能把旧勾选迁移到新成片。

旧无轮次请求只在素材轮次仍为 0、没有终止的上传交接历史时接受普通首传，并继续严格业务防重；否则返回明确“页面版本已更新，请刷新”的协议错误。旧 token 能精确匹配历史回执时仍可查询重放。旧页面没有明确失败重试 ID 的请求不得隐式新建第二次交付。

### 15.4 权限与操作人不能混淆

代码证据：`accounts.allowed` 当前权限是项目 owner 或管理员；`material_workers._job` 将 actor 写成 owner。新上传请求必须从认证上下文记录实际 actor，不能接收前端自报或把管理员操作伪记为 owner。

- owner 保持现有公平调度分组；actor 用于审批、取消和审计，二者分开。
- 点击、取消交接、进入外部写入前重新读取 actor 是否 enabled、是否仍可访问项目；浏览器退出登录不撤销已接受后台任务，账号禁用/权限撤销才阻止新的外部写入。
- 管理员取消他人任务遵从现有管理员权限，并记录管理员身份、目标任务、确认的版本/SHA 和后续 delivery。普通用户不能凭 task ID 取消无权项目。
- 如果权限撤销发生在外部调用已经发出后，不能声称请求已撤销；保留回执和现有核实流程，禁止盲目重传。
- actor 只能作为新记录的可信扩展。历史缺 actor 的任务沿用既有恢复规则，不凭空认定某个用户重新审批过。

### 15.5 不引入部分制作和新的无关业务限制

撤回第一版中“整项目确认时跳过冲突素材”的提议：本次不改变整批确认的事务语义。冲突只检查本次实际要制作的素材，原本无变化而被跳过的素材不影响其他素材。

失败候选并非永远阻止上传：若已无活动执行器、没有可迟到提交的结果/恢复任务，当前旧成片仍可被明确预览确认。前端必须展示正在确认的是旧当前版本；不能因为 candidate_version 字段还存在就永久封死。

识别/跟踪等活动的“正在进行”才加入提醒；已经完成且只产生建议的报告不是一份待替换成片，不应要求用户逐份放弃所有历史报告。只有仍可被确认替换的实际成片结果需要明确放弃。

### 15.6 取消与替换的锁冲突要有可执行路径

当前 replacement 准备线程长时间持有排他 gate。如果取消请求也必须先拿同一 gate，用户会永远无法请求停止持锁任务。方案要求：

- 取消接口先在任务自身短状态锁内写入绑定任务/attempt 的取消请求并释放锁，不等待替换 gate。
- 替换在提交前读取取消记录，并在与取消方共享的短原子裁决锁内决定 commit/cancel；固定为 gate → media lock → 短任务裁决锁。取消方只持任务锁写标记，释放后才进行其他操作，不能反向等待 media lock。
- 已进入不可分割 commit 的任务返回“提交已开始”，不能仍声称可取消；完成后以 current_version 结果为准。
- 等待上传意图和取消授权先持久化，协调器再请求停止；这样崩溃不会留下“编辑停了、用户选择丢了”的交接空洞。**这是普通准入 gate 流程的明确例外**：建立 waiting_edit_stop 只写父请求元数据，不修改成片，因此不先等待被替换准备持有的 gate；在 media lock 及短任务裁决锁下核对源版本/冲突任务身份并持久化。替换提交在同一裁决范围检查 waiting 意图，已被取消授权覆盖的任务不得提交。真正转为 delivery 时仍必须取得 gate 并再次完整核验。
- 这里必须与另一任务最终锁序一起核验；若现有实现采用不同顺序，统一调整并做多进程死锁测试，不能照搬两套相反顺序。

### 15.7 文件准备、空间与调度阻塞

代码证据：`material_workers.materialize` 复制整份视频，`recover_outbox` 在 `webserver.worker_tick` 最前调用；现有复制发生在 upload 槽位/存储准入之前。大量并发确认后，单把 upload=1 并不能限制预先复制的文件数量和 IO。

实现要求：已接受时只持久化固定版本引用与任务描述；大文件副本准备放到获得上传资源和磁盘预算之后，沿用原有独立副本、哈希校验和不可覆盖约束。必须一起调整子任务输入指纹/结果证据与恢复时序，不能简单删掉复制或绕过 stage fingerprint。

如果沿用现有 materialize 结构，必须做到等价的有界准备（上传池准入与准备共用容量、复制前预算预留、独立执行且不阻塞整个调度 tick），并证明不会无界预拷贝。实施只选择一种路径，不叠加两套容量。

磁盘不足保持排队或明确阻塞原因，不取消用户已经接受的意图；不能凭文件缺失当作没提交过。被 waiting/queued 请求引用的版本、任务状态及回执禁止被删除/清理。临时准备文件中断只能清理本次执行拥有的文件，不能删除原成片、历史结果或 OSS 对象。

文件名/目标 OSS 键的已有冲突校验保持原样。跨项目同名不是同一个素材的重复提交，不可按 SHA 相同直接合并业务任务；目标 forbid-overwrite 和飞书原记录核验继续兜底。

### 15.8 恢复不是新的授权，外部写入不承诺绝对一次

- 本地原子事务保证同一意图不会创建两个可执行 delivery；外部服务超时仍可能产生已写入但未收到回执的结果。对这种情况保留 unverified，不宣称能靠重试实现绝对一次。
- 协调器多实例/重复 tick 可共同发现同一记录，但状态转换必须按请求 ID + 当前状态/轮次原子执行，delivery ID/outbox ID 在首次转换中固定。取消适配本身也必须幂等。
- 启动恢复只恢复已持久接受的意图；不把扫描到的旧 session 或 failed 任务自动变成新上传。
- waiting 请求的目标指纹在确认时冻结；执行前校验目标配置。配置变化停止，不悄悄上传到新桶/新表。
- 维护期间停止新交接和副作用启动，可继续记录已有进程退出/回执；新协调器纳入服务健康和排空清单。不能只在 HTTP 检查维护文件。

### 15.9 前端和错误回执细节

- 所有新增状态及错误在单素材显示。重复请求返回已有失败/待核实状态时，不显示“上传成功/已加入队列”；blocked/cancelled 用 HTTP 200 返回原请求状态供恢复，409 用于新的请求无法接受。
- 原方案的 `upload_submission` 补充拟新增 `reason_code`、`message`（无原因时 null），用于持久状态恢复；不能只靠弹出一次 toast。其他项目详情仍是当前状态。
- 成功持久化之后详情投影或 audit 写失败，应尽可能返回最小稳定 upload_submission 回执；客户端拿不到回执仍按结果未知处理，服务端不得回滚已接受任务或鼓励创建新 token。审计失败可由持久请求证据补记，不能导致重复交付。
- GET 详情提供当前素材的有效/最近终态请求摘要，完整历史按已有管理方式读取，不把全部任务历史铺进每次轮询。
- 点击 A 的冲突对话框必须固定 A 的身份；切项目/素材后关闭或明确保留绑定，确认时不可重新读取 current 中的 B 作为对象。
- 新增“撤销后续上传”只针对尚无 delivery 的请求。原方案仅提行为但漏了路由，拟新增 `POST /api/batches/{id}/upload-requests/{request_id}/cancel`，body 仅接受 submission_token；这里 request_id 是上传请求 ID，避免与素材 ID 混淆，代码变量使用 upload_request_id。鉴权、幂等、同事务裁决；已有 delivery 返回明确冲突。

### 15.10 升级与回滚不是只读兼容

schema_version=1 可读不代表旧代码会执行新冻结规则。旧版本不知道 upload_requests，可能在 waiting_edit_stop 期间启动编辑；因此即便数据能解析，也不能混跑新旧 worker。

发布流程必须维护排空、单一执行所有者、同步更新前后端。旧页面按 15.3 的兼容策略处理；不自动解释缺少取消/轮次字段为同意。

回退前：禁止新提交，取消/终止全部尚未转交的请求并等待必要编辑取消终态，核对已入队 delivery 已交给旧版本认识的状态，再运行现有发布回滚程序。不能靠恢复旧数据库抹掉新接受任务。尚无法安全排空时停止回退，不能带着不被旧版识别的冻结记录启动旧 worker。

### 15.11 本轮新增验收门槛

- blocked/cancelled 终态、项目暂停恢复不自动复活上传；编辑仍运行时保留编辑保护但不留下永久上传占位。
- 撤销之后到达的已知 token 重放与从未见过的旧 token 均不重新入队；其他素材的轮次不受影响。
- 取消碰到持有 replacement gate 的线程仍能写入停止请求；commit/cancel 使用真实多进程屏障测试，无死锁、无双赢。
- 管理员代提交保留真实 actor，owner 调度不变；账号禁用/权限撤销在副作用前被阻止，退出登录不误取消任务。
- 连续接受大文件时，获得执行预算前无无界复制；磁盘不足不丢意图，其他 poll/任务调度仍能推进。
- 持久化成功后模拟详情计算失败、audit 写失败和响应丢失，重放仍只存在一条交付。
- 整批制作保持原有事务语义；候选失败终止后可明确上传旧片；已完成建议报告不误拦。
- 旧页面、旧 mutation、轮次缺失、旧 worker 兼容/拒绝路径以及回滚排空均有实际用例。

第二轮结论：依赖已明确，方案缺口已记录并修正；仍须拿到另一任务最终实现做锁序/状态契约核对。当前没有依据声称所有实现风险已经消除，也不需要用户再重复确认已明确的业务规则。
