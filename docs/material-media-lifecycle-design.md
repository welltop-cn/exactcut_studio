# 同一项目内素材增删改与媒体版本设计（Grok 审查稿）

日期：2026-10-11。状态：设计审查，尚未实现或发布。本稿中的新字段是拟新增的内部持久化契约，不是现有 API 字段。不得根据本稿执行 OSS 删除、修改桶生命周期或改动其他应用对象。

## 目标与已核实的现状

用户希望一个项目包含多条身份稳定的素材，每条素材只展示一份当前成片和对应预览；重新制作失败不能丢失旧成片；新增、编辑、删除及 FBBM 交付不能互相串数据。媒体由 OSS 直传给浏览器，应用只负责鉴权和签名。

已核实源码：`workflow._clone_batch(purpose='repair')` 创建新 batch ID 并 `allocate_sequences(all_new=True)`；`_save_draft` 不允许已确认项目编辑；`_start_batch` 的重试直接读取原 confirmed.json；`orchestrator.execute_batch` 在制作开始覆盖结果记录，成功后 `os.replace(staged, output)` 替换同名本地成片；`result_store.put` 仅保留心跳字段。因此不能靠更改 OSS 路径实现同项目版本管理。

`result_store` 已有每素材 fcntl 文件锁与原子 JSON 写入，可沿用；`batch_control.LOCK` 是进程内线程锁，不能承担跨进程提交保护。现有命名锁和执行租约仍需保留，不能新增相反的加锁顺序。

## 身份与路径

- 项目沿用 batch UUID；素材沿用已有 request_id，首次纳管即成为不可修改、不可复用的 asset ID。新素材由服务端分配 ID。前端行号、排序、素材序号、标题均不能参与身份匹配。删除后同名新增也必须分配新 ID。
- 明确拆分“复制项目”和“修改后重新制作”：复制仍创建新项目和新素材身份；重新制作留在原项目，保留素材 ID 与已有展示序号。新增素材才分配新序号。历史 clone 项目不凭标题或序号自动合并。
- 每次确认制作生成新的随机 version ID，绑定不可变的素材输入快照与媒体配置指纹。每次执行重试另有 attempt ID；两个执行尝试不能共同写同一目录。变更字幕、剪辑、封面、嵌入字幕、导出命名等任何影响文件或交付语义的字段都创建版本；只有不参与产物/交付的 UI 备注、显示排序可原地修改。
- 新输出位于 `production/versions/<asset-id>/<version-id>/<attempt-id>/`；先写临时文件，再在本目录落定。不能覆盖旧版本本地文件。旧的 `production/videos` 和 `previews` 文件在纳管后只读保留，不移动、不删除。
- OSS 保持专用前缀 `exactcut-previews/production/<batch-id>/<asset-id>/<sha256>.mp4`。master 和 preview 字节相同可引用同一对象，否则各自一份。内容哈希对象不可覆盖。版本记录存 key/hash/size/上传校验回执，不存临时签名 URL。

## 唯一权威记录与兼容性

新增项目内 `media-state.json`，延续仓库 schema_version=1，在独立 `media_state` 模块定义、校验内部格式。拟包含：项目 revision、各素材的 immutable ID、desired_generation、deleted_at、current_version、candidate_version、版本及尝试记录、待调度事件、交付快照引用。素材版本记录包括输入快照、generation、状态、master/preview 本地路径与 OSS 回执、失败原因。删除保留 tombstone。原子写入这个文件是逻辑提交点。

只有该记录决定新版项目的当前媒体与候选状态；confirmed.json、results.json、每素材结果文件与 runtime 是兼容读取/执行进度投影，不能反向覆盖权威状态。带纳管标记的项目不能因主记录缺失或损坏退回旧结果：报告可恢复错误并阻止写入，避免静默回滚。投影带权威 revision，读取发现落后时根据权威记录重建。不能让两个持久化来源各自决定“当前版本”。

首版使用一个项目级跨进程 fcntl 锁保护 revision、素材代次、提交、逻辑删除和交付意图；网络、渲染、文件复制和哈希在锁外执行。锁文件固定在项目外的专用锁目录，项目逻辑删除后仍保留，避免旧进程与新进程锁住不同 inode。写入沿用原子替换机制，并检查现有 write_json_atomic 的 fsync/目录持久性，补足崩溃恢复需要的语义。

统一顺序：全局命名锁 → 项目媒体锁 → 现有素材结果锁；不允许持有结果锁再获取项目锁。执行租约与新状态检查的嵌套关系须逐调用点审计，长执行租约不等同于提交锁。项目级短临界区不会串行化视频制作。

## 增、改、删和恢复

### 新增 / 保存编辑

客户端提交基于哪个项目 revision；服务端在锁内校验，旧 revision 返回冲突，绝不最后写入者覆盖。已有素材 ID 必须属于本项目且未被替换。新行以独立 client mutation ID 保障重试幂等，服务端分配新素材 ID。保存草稿与确认制作分开：保存不改变 current_version。

每次保存影响制作的编辑，即递增该素材 desired_generation，使尚未发布的旧候选失效；没有变化的素材不变。确认时记录输入快照、version/attempt ID 与代次，并把调度事件与候选记录写入同一次 media-state 提交。后台根据持久化事件调度，重复事件通过 attempt ID 去重，进程崩溃后可恢复，不能只靠先写 JSON 后直接启动进程。

确认后逐素材制作和发布，不等待其他素材，也不改动未修改素材的 current_version。UI 同时显示“当前可用成片”和“新版本制作/上传中或失败”，不能让制作失败把旧预览按钮变灰。

### 候选发布

状态：已排队 → 制作中 → 质检通过 → 上传中 → 可发布 → 当前成功版本；另有失败、取消、已取代。成功必须同时具备 master 和匹配 master hash 的 preview，两者本地校验与 OSS 校验完成；预览失败或任一上传失败都保持旧 current，新素材暂时没有 current。

提交前在锁外完成文件与 OSS 校验；在项目锁内重读并比较：素材未删除、generation 等于任务代次、candidate/version/attempt 完全匹配、当前候选没有被取消。一个原子写入同时切换 master 与 preview 所属版本，记录旧 current 为历史。任何条件不符就把完成结果记为已取代，不得发布。每个任务的进度/失败/回执写入也要按 version/attempt 合并，禁止旧任务写整个项目快照。

上传失败可复用同一版本已经校验成功的文件重试上传，不必重新渲染；重渲染使用新 attempt。任一执行租约丢失后，旧 attempt 无权提交。实例重启时恢复候选，不凭文件存在推定已成功。成功上传但提交前崩溃留下未引用对象，仅登记并保留。

### 删除 / 撤销删除

本期只做逻辑删除：锁内 tombstone + generation 递增 + 候选失效 + 持久化取消事件。同一次提交保证迟到任务无法重新激活素材；停止进程只是节约资源，不是正确性的前提。HTTP 鉴权后检查 tombstone，拒绝新签名、新下载跳转、新审批；已签发的 OSS 链接仍可在有限有效期内使用，不承诺立即撤销。

删除项目也只逻辑删除，包括拦截现有 `delete_batch` 的物理目录删除路径，防止新业务仍被旧接口清空。用户仍可恢复逻辑删除记录；本期无自动过期清除。恢复保持同一素材 ID 和历史 current，但 generation 再递增，不复活旧任务。涉及正在交付或结果不明的素材/项目，删除被阻止并提示先核对交付；不会伪称外部交付被撤销。

## FBBM 审批与交付

审批绑定 batch + asset + version + master SHA256 + 交付参数快照。新审批只能针对当前成功版本；入队时再次校验审批仍指向当前版本、未删除且未撤销。入队后生成独立 delivery ID，固定版本引用；后续新版本完成也不能把已排队的交付偷换成新版。UI 分别显示“当前版本”和“正在交付/已交付版本”。

先持久化交付意图和目标键，再执行 OSS 内部 CopyObject 与 FBBM 请求，沿用现有 intent/unknown 防重机制。复制仅用对应版本的私有 master，源 hash/size/ETag 与目标 forbid-overwrite 校验。正式交付对象维持原有目录与访问策略，不跟随素材编辑变化。交付记录按 delivery ID 存历史，现有每 request 单槽 publications.json 只能作为显示投影，不能覆盖历史证据。

如果同一展示文件名已交付其他字节，不覆盖也不自动编造 FBBM 文件名后缀。首版在新交付前明确拒绝该命名冲突，保留新成片可预览下载，要求使用现有业务允许的唯一交付命名重新确认。后续只有查明 FBBM 命名契约才自动分配新的交付序号；素材身份始终不变。

## 历史纳管、上线与回退

1. 先只读盘点并备份项目元数据，列出重复 ID、缺文件、输出 hash 不符和交付未知；异常项目不自动纳管。既有数据绝不凭文件名猜关系。
2. 纳管时阻止该项目新任务，等执行/交付租约退出。把 confirmed 中的 request 与经过核验的结果、预览 master hash、交付 hash 对齐，生成初始不可变版本与权威记录；原文件不改动。没有合格预览的旧成片作为 legacy 当前可用版本，后台补预览/OSS，不把原来能下载的成片隐藏；只有后续新版本切换才要求成对成功。
3. 上传与补传使用固定版本身份；回执只能合并到对应版本。已有对象先核验，已存在且不匹配则报错，禁止覆盖。迁移幂等，提交前崩溃重试，提交后投影未更新可重建。
4. 首版以项目 feature gate 灰度，不直接全量重写。所有能修改素材/结果/发布的入口（网页、CLI、定时任务、历史补传、手动预览、删除 API）都必须识别纳管状态，未改造的写入口明确拒绝。
5. 上线前验证所有旧 worker 已退出，不能新旧写者并存。保留兼容读取但**不能直接回滚至不识别新状态的旧二进制**继续写数据。回退先进入维护只读，使用支持新状态的兼容版本；必要时从备份恢复到独立路径核验，绝不用旧 results 自动覆盖新状态。

## 物理回收与容量

本期没有 DeleteObject、批量删除、生命周期规则，也不改桶 ACL/CORS。现有用户“不要删除 OSS 数据”的要求持续生效。历史版本、逻辑删除和未引用对象保留，明确会增加容量；容量不足时停止新制作/上传，保留已有版本，不以自动删除解围。

未来若获明确授权，才另做回收：仅删除本应用登记的对象，核验专用桶/前缀归属、全局所有引用（当前、候选、历史保留、交付与签名租约），与新增引用采用共同并发协议，超过签名 TTL 和传输缓冲后逐对象审计删除；不使用目录递归清理，不触碰正式交付或其他应用对象。本期不实现这个执行器。

## 必须通过的验收

- 同项目修改保留 batch/asset ID 和旧成片；复制项目分配新身份；排序/删除中间行后其他素材 ID 不变；新增重试不重复建素材。
- 两浏览器同时编辑只有匹配 revision 的提交成功；旧候选在新编辑后完成、重复任务、租约丢失、删除后迟到上传均不能改 current。
- 新版渲染失败、预览失败、任一 OSS 上传失败时旧预览/master 不变；成功时成对切换；同内容复用对象且不再上传。
- 在调度提交、文件落定、两次上传之间、current 切换前后、投影更新之间注入崩溃，可恢复且不会返回半新半旧媒体。
- 删除/恢复/项目删除与制作、补传、签名、审批并发；旧物理删除入口被保护；目录外路径和他项目素材 ID 被拒绝。
- 已批准旧版但未入队时 current 改变会拒绝；已入队的版本固定；FBBM unknown 不重复交付；命名冲突不覆盖既有交付对象。
- 历史迁移幂等，缺失/不一致记录隔离，不合并历史 clone；旧写入口拒绝，纳管主记录损坏不回退旧数据。
- 全套本地/Linux 测试、Grok 方案及实现复审、灰度浏览器切项目和视频预加载期间刷新/正式下载测试均完成后发布。不得仅以单元测试宣称线上已解决。

## 待审查重点

请判断权威记录的原子提交是否足够、跨进程锁和执行租约是否存在死锁或遗漏、历史纳管/只读回退是否完整、发布与交付状态是否存在数据丢失窗口。若该方案范围过大，请指出可独立安全交付的阶段边界，不能通过省略 fencing、历史保留或禁删约束简化。所有现有字段/行为以附带源码为准；上文新字段为设计提案。

## R2：针对 Grok 首轮审查的约束与实现收敛

本节优先于前文不够具体的描述。首轮审查记录于独立 review 文档；不把新调度器、交付器与旧调度器并行重写，而是复用现有阶段作业，在业务项目内部隔离候选。

### 权威提交和候选隔离

`media-state` 同时保存完整可编辑草稿、revision、素材 desired_generation、幂等请求摘要/结果、当前/候选版本和 outbox。保存草稿与代次失效在一次原子写入内完成。对确认、删除、恢复、审批入队同样比较 revision，并对幂等键相同但正文不同的请求拒绝。

候选通过一个**内部执行批次**复用现有下载、渲染、资源控制和阶段恢复：新内部 UUID、不可变输入快照、单素材、稳定父素材 ID、隔离输出；用户看到的项目 ID 不变。这是内部执行容器，不展示为新业务项目，不重新分配原素材展示序号。内部批次被列表过滤，不能通过公共 HTTP 接口直接编辑、删除、启动、审批；其父项目权限决定所有用户访问。对内部批次的命名检查只允许复用已预留的父素材名字，不能抢其他项目名字。复制项目仍创建独立业务身份。

每次重试创建新的内部批次/attempt，不重用输出目录。parent outbox 在同一提交中预先指定内部 ID，创建内部目录和进入既有调度队列都按该 ID 幂等恢复；重复调度不能生成第二个候选。内部阶段任务沿用现有 job/attempt/process token 校验。`execution()` 是心跳记录，**不是持有互斥锁的执行租约**，不得把它当作防重依据。

旧或重复 worker 最多污染自己的候选目录：父项目可访问的媒体只来自独立封存目录 `production/versions/<asset>/<version>/<attempt>/`。完成阶段复制 master 与 preview 为新文件，核对源记录、复制后实际 SHA256、预览的来源 master SHA256、各自 OSS 回执，并把该目录封存；封存完成后不能用普通渲染器写入。禁止硬链接到可写候选。复制或校验失败不改当前版本。

内部候选的自动上传使用父项目/素材身份写专用 OSS 哈希键；封存副本通过实际字节哈希核验后才能重绑定本地文件身份回执，不重复传视频。最终在父项目锁内严格检查 `attempt.generation == asset.desired_generation` 且候选 version/attempt ID 均相等、未删除未取消，再成对切换。若已失效，仅记录该 attempt 已取代。未通过该提交的候选永远不能由父项目预览/下载/审批访问。

不再允许旧 `result_store` 分片决定父项目状态：它们仅属于内部执行容器。父项目展示由权威 current 和候选进度组成。父项目所有老写入口显式改道或拒绝，不能把内部 `failed/processing` 覆盖当前成功版本。子任务失败/心跳仅更新自己的执行记录，最终状态合并父记录必须带版本 ID 和代次。

### 锁、暂停与恢复

新媒体模块不在项目锁内调用任何会申请旧 `batch_control.LOCK`、runtime.lock、publications.lock、结果锁的函数；也不允许持有这些旧锁进入媒体模块。外层全局命名锁只能在需要预留名称时先取，锁内只做名称检查/CAS，不做片源探测、哈希或网络请求。旧锁与新项目锁保持不嵌套，避免用一个涵盖全系统的大锁顺序扩大临界区。所有对应入口需要测试锁调用关系。

outbox领取在父项目锁内提交，锁外创建内部容器/入队；已存在确定 ID 的任务核验内容后复用。领取到排队之间的崩溃由 outbox 恢复，不允许“claimed 就永远不重试”。需要真正新执行时先在锁内使旧候选 attempt 失效并分配新 ID，再启动。父项目暂停、归档、逻辑删除阻止领取；暂停不会被当作进程死亡。候选恢复仍遵从原有作业实例/进程身份协议；跨实例身份无法验证视为仍可能活跃，不纳管也不物理删除。

部署假设明确为一台 Linux 主机的本地持久磁盘；不声称支持多主机共享数据根。锁与独立纳管索引位于项目目录外。权威文件写入需要文件 fsync、rename、父目录 fsync；高频心跳不重写整个 media-state，只有状态转换才提交。

### 交付与历史

每个 delivery ID 使用独立不可变的内部交付批次来复用现有 write-ahead intent、unknown 和验证逻辑；其单素材 publications 槽只属于这一次 delivery，不再随父素材的新版本覆盖。父记录固定指向 delivery/版本/master SHA/目标参数快照。进入外部副作用之前父 outbox 和内部交付意图均需持久化；中途崩溃保留 pending/unknown 并拒绝自动重复。

同一父素材任一版本只要仍有待交付、上传中、轮询中或 unknown，就拒绝新的交付入队；恢复旧结果不得释放尚未核实的交付阻断。当前变更只使尚未入队的审批失效，不修改已入队的快照。全局命名预留与 forbid-overwrite 共同防止跨项目同名不同字节覆盖。已交付名字发生冲突则明确拒绝，不猜测 FBBM 新命名规则。

`master.sha256`、`preview.sha256` 分别是各自文件哈希；`preview.source_master_sha256 == master.sha256` 才是来源关系（映射现有 preview.master_sha256），**不要求两份不同文件的哈希相等**。

输入图、字幕等也是不可变依赖：新上传写新哈希路径，版本快照存路径及哈希，禁止复用会 unlink 旧输入的接口。已有素材 ID 保留历史合法 request_id；新 version/attempt/delivery/内部 batch ID 用服务端 UUID，不能照搬“所有旧 asset ID 必须 32hex”的建议而破坏历史 Rxxxx 身份。

历史纳管先检查分片和 legacy 汇总冲突、批内重复文件名、交付 SHA 与本地 SHA 关系。不同就隔离，不把旧交付绑到新字节。父项目纳管后 feature gate 只能禁止新增纳管，不能切回旧写路径。外部纳管索引缺失/冲突或 media-state 损坏时停止写入，不能降级读旧分片；目录外索引用于拦截遗留删除入口。

本期素材/项目删除仅提交 tombstone、代次失效和取消事件，不运行原 delete_batch 中的 rmtree、导入目录/反馈/作业删除。恢复不复活旧任务。部署前所有旧 worker 排空，纳管后不允许回退到不认识新协议的二进制。

### 上线核对

上线前只读核验 OSS 的既有生命周期是否覆盖专用前缀，发现删除规则就阻止启用，不改桶规则。其他应用清理任务若无法穷尽验证，明确记录限制，不能宣称已证明任何外部清理都不存在。

实际服务器测试要求见 `docs/verification/material-lifecycle-server-acceptance-plan.md`。阶段可独立验收，但对外不宣称仅 OSS 卸载等同于同项目 CRUD 完成。本次最终交付目标仍包含安全的同项目增删改、版本切换、交付绑定和真实服务器验收；关键阻断未消除保持旧线上版本。

### R2 复审补充：双恢复与命名别名（实现前置测试）

Grok 同会话复审确认原 7 项阻断已闭环，允许开始权威状态/封存/逻辑删除实现；接入既有调度与命名扫描前必须通过以下失败测试。

1. 父 delivery outbox 只负责补建同一内部容器和首次确定性任务。内部 intent 一旦存在，外部副作用与未知结果由该不可变 delivery 的意图状态约束；缺作业不能触发第二轮发布。父 delivery 状态单调保留 pending/unknown，不根据恢复后的内部槽自动变为可重新交付。注入父 outbox claimed + 内部 unknown + 作业缺失，再同时运行父/内部恢复，断言外部发布次数不增加；只有绑定原回执的明确核实才可解除未知状态。
2. 全局命名扫描将内部 confirmed 视为父素材预留名的别名，不作为新的占用者触发父素材改号；父项目的预留继续阻止第三个项目占用。内部容器不能调用 all_new 分配或 repair clone。注入父 confirmed + 同名内部候选，再保存父草稿与第三方项目，断言父序号不变、第三方不能占同名。
