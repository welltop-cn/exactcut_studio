# 剪切打码资源冲突与等待体验优化方案

日期：2026-10-29。状态：Gemini 3.8 Flash High 二次审查通过，可进入实施；当前仅完成方案，未实施、未部署。

## 目标与证据边界

减少短暂锁冲突直接暴露的429；等待可理解、可取消、不会重复执行。保持全局计算资源上限、素材版本校验及交付互斥，不通过取消锁或无界并发消除429。

历史证据：producer05在10月28日17:15:16打开编辑器、17:15:34启动识别被429拒绝；17:16:28–17:17:18识别完成。另一素材首次打开耗时20.765秒，新建会话路径包含复制、哈希、完整帧时间戳校验，尚无分阶段耗时。没有打码跟踪提交记录，不能将这次等待归因于SAM。亦不能证明浏览器主线程卡死。

## 已核对实现

- cutting.lock_file非阻塞冲突统一抛CutError(429)，不能区分compute/frame/scan/asset/batch锁。
- cutting_access.gate的批次锁冲突转409，素材锁仍可返回429；409也包含交付锁定、版本改变，绝不能统一重试。
- mosaic_http外围有batch_lease，所有路由可能先在这里拒绝；现有错误正文只有error。下述code等为**拟新增契约**，不是现存字段，实施必须同步服务端和消费者测试。
- 本地frame_lease已有2秒有限等待、获得锁后重新检查帧缓存；不要重复添加第二层服务端等待。上线状态须在实施/发布前重新核对。
- mosaic.js loadFrame已有AbortController、token/epoch，scanLoading等已有提交保护。取消fetch不等于取消已在服务器运行的抽帧。
- mosaic_scan.start对相同identity运行任务复用；已完成且force=false时复用，force=true可能重跑。render有recipe和缓存；clip-preview不写render-latest。不能认为GET render latest足以恢复所有POST。
- 初次open同步准备文件并probe_source；已有会话快速返回。

## 第一阶段：明确错误契约和有限恢复

### 服务端

拟新增明确的资源忙错误类型，经cuts/mosaics统一序列化：保留error，增加code=editor_resource_busy、retryable=true、resource（可重试白名单仅frame/compute/scan）、retry_after_ms=1000，并发Retry-After: 1。只在确定任务尚未受理的锁冲突点返回。实现前核对respond及诊断包装器，避免字段丢失或重复分类；保持schema_version=1。

默认不为所有CutError或所有429标记可重试；维护503、源版本改变409、已交付、参数错误、外部Gemini429、未知错误均不自动重试。首期asset/batch/worker锁冲突均不自动重试，保持原状态码并给出准确提示，不猜测锁持有者。版本变化409立即终止重试，提示刷新，禁止自动换用新SHA提交旧选择。

不改全局compute/scan容量。不在持有多把锁时新增长时间阻塞；失败路径释放已取得的锁，然后由客户端有界退避。frame沿用现有2秒等待并复查缓存。先记录具体冲突资源和耗时，后续有证据再调整容量。

### 前端

新增局部编辑器资源忙重试助手，不全局拦截所有fetch。仅白名单操作+明确上述code/retryable触发。open与scan(force=false)初次请求之外最多3次，退避基准1/2/4秒加0–250ms抖动；遵循Retry-After且不能超过剩余等待预算。资源忙重试阶段总预算15秒（含重试请求耗时），不是把成功受理的20秒open截断为15秒。

每次重试前校验epoch、请求token、batch/session、source_sha256、reset_at、操作选择版本；原始POST请求体只快照一次。页面隐藏、切换素材、关闭、改变选择、用户取消时取消计时器和未完成fetch；无效回包不得写UI。一次用户意图只运行一条重试链，重试层不叠加现有轮询。等待期间沿用按钮禁用，显示“处理资源暂忙，正在重试（1/3）”，保留选择，达到预算后提供手动重试。

取消等待仅取消客户端自动恢复，不承诺撤销已受理任务。收到任务ID后进入现有状态轮询；停止计算使用现有stop协议。响应丢失则显示“正在核对任务状态”，不能把网络AbortError/timeout当资源忙重复POST。

### 操作矩阵

| 操作 | 明确受理前资源忙 | 网络断开/响应丢失 |
| --- | --- | --- |
| GET准确帧 | 最多重试1次（1秒+抖动），超限使用现有mosaicFrameRetry按钮；同一意图串行，拖动只取最新帧 | 不套用资源忙重试，保留现有取消语义 |
| POST open | 明确未受理时重试原始素材+哈希 | 不盲重发；首期提示手动重试/恢复已有会话 |
| POST scan(force=false) | 明确未受理时重试同一快照 | GET scan核对reset/身份和状态；无法确认则提示状态待核实，不自动重发POST |
| POST scan(force=true) | 首期不自动重试，即使明确429也保留手动入口 | 只查询当前状态；不能仅凭completed认定本次成功，不自动重发。无法确定时明确提示再次手动识别可能产生新任务 |
| POST render/clip-preview/track/locate | 首期不开放POST自动重试，先明确其幂等与查询契约 | 不凭render-latest恢复clip-preview，不盲重发 |
| replace/discard/stop/上传 | 不进入通用自动重试 | 沿用各自恢复协议 |

识别初期优先覆盖open/frame/scan(force=false)。后续要开放生成任务的网络恢复，另行设计持久操作ID与按ID查询，使请求ID、配方、任务ID一一关联；不能把HTTP trace/client_request_id冒充幂等键。

实现范围补充（架构师审查后）：本轮 scan 恢复仅覆盖默认统一编辑器 mosaic.js；旧剪切入口 cutting.js 只接入 open/frame，其 scan 恢复另行跟进，不计为本轮已完成能力。浏览器 retry 事件首期只提供资源、身份与耗时，操作类型、attempt、链标识及取消终态尚未实现，因此“请求数/意图”和完整恢复率仍是后续诊断验收目标。

### 减少请求冲突

直接复用已有100ms seek防抖、AbortController、prepare()的preparing Promise Map及128帧缓存，不另建一套去重机制。只补同帧未完成请求复用的缺口测试和重试定时器取消；新seek立即清除旧重试。取消前请求无法停止服务器工作，需记录frame生成/缓存命中，验证优化是否确实减少计算。跨用户仍由现有frame锁控制，不先增加多进程并发。

## 第二阶段：首次打开的长等待

先增加copy/hash/probe基本信息/probe全帧时间戳/总耗时诊断，不删全帧安全检查。现有open()已立即打开对话框并显示首次准备提示，允许关闭及重新进入复用请求；这部分直接保留，首期只补耗时观测与资源忙提示，不重新开发加载界面。不能给未测得阶段编造百分比。

如果测量确认首次校验是主因，再单独设计异步session preparation：以素材版本SHA和批次素材身份去重，原子状态、重启恢复、有限队列、工作量上限、最终版本复核，source.mp4及session.json只在验证成功后发布。这是后续独立变更，不与第一阶段重试补丁捆绑。

## 第三阶段：定位“框选卡住”

为用户动作→请求→回包→渲染增加时延记录，采样记录长任务/事件循环延迟（浏览器能力探测，不支持时降级），绑定page/session/action，不收集画面、候选文本、视频URL或用户输入。错误分类和重试次数需进入已有诊断通道，尊重现有限额；旧页面仍缺数据时明确诊断限制。

## 验证与发布门槛

1. 跨进程锁冲突：每种锁返回准确分类，旧error保留，资源忙发生在任务持久化/线程启动之前，失败释放锁；非资源429/409不得触发自动重试。
2. fake timers验证次数、抖动范围、Retry-After、15秒预算、取消、页面隐藏、关闭重开、素材和版本切换、两标签页；超限保留草稿。
3. 服务端已接收但响应丢失：scan(force=true)不得重复付费调用；clip-preview不误恢复其他任务；重试期间另一个标签页启动任务时只复用相同身份任务。
4. 抽帧快速拖动最终帧正确、旧回包不覆盖、并发解码不突破现有上限；原片播放不因frame争用被阻断。
5. 使用隔离合成视频和假识别服务，不调用真实AI/交付，不修改生产数据；首次打开慢请求测试确认不会被资源忙预算误取消。
6. 对比资源忙次数、恢复成功率、请求数/意图、抽帧生成次数、P95等待、取消后后台任务残留；重复任务与陈旧UI更新必须为0。等待时间不承诺在资源长期占用时降低。
7. 完整回归、独立审查、测试实例验收后另行获得发布指令；正式走release manager。只回滚代码，不回滚业务数据。

## Gemini 审查后的端到端补充

- 明确改动范围：cutting.py/cutting_access.py及两个编辑器HTTP适配器、webserver.py、error_guidance.py、web/app.js和编辑器JS。第一步先完成错误契约集成测试，再接重试。
- respond()目前通过{**body}保留顶级字段，并不会删除code；但没有Retry-After参数。拟增加受限的retry_after整数参数，禁止任意响应头注入。显式提供与顶级code一致的error_info，保留脱敏及trace_id机制。
- api()目前仅抛字符串Error，确实丢失结构化信息。拟让Error保留原message，同时附加经过校验的status/code/retryable/retryAfterMs字段；原调用方不变，全局不自动重试。直接fetch的准确帧路径复用同一错误解析器，成功JPEG仍走原流程。
- api()支持可选外部AbortSignal，与既有超时控制合并；区分主动取消和请求超时。共享preparing Promise不能因一个消费者取消就无条件中断其他消费者：关闭只撤销该消费者的等待与后续重试，保留有效消费者；全部失效后也保留已发出的open请求直至正常结束/原120秒超时，以继续支持关闭重开复用；只取消尚未发出的自动重试。其他非共享请求才由消费者信号取消。失效后不得启动新重试，及时移除监听器与定时器。
- 首次收到明确资源忙后记录15秒截止时刻。截止后不再发请求；若截止前已发出的open尚未返回，不以资源忙预算强制中断可能已经受理的视频准备，沿用原open超时并显示准备中。故15秒是自动恢复调度窗口，不承诺请求完成总耗时上限。准确帧额外重试最多一次，服务端等待与实际解码耗时分开测量。
- 服务端忙错误→respond包装→Retry-After→api结构化异常→编辑器重试→取消完整集成验证；有现存submission_token不代表scan端消费了它，不能据此宣称扫描已幂等。

## 审查意见取舍记录

Gemini初稿结论：需修订再实施。已采纳结构化异常与Header透传、force=true首期不重试、asset/batch不自动重试、frame最多一次和复用现有防抖/单飞设施。

核实后不照搬的判断：respond并未抹除顶级字段；确认为未受理的force请求重试本身不必然重复计费，危险的是受理结果未知后重放，本版仍保守禁用；有限重试遇版本409会停止，不等于死循环；ThreadingHTTPServer线程积压是待测风险，不是本次线上已证实根因；只读审查本地代码不能证明相关改动已经上线。状态锁存在blocking=True，也不能由部分LOCK_NB推导整个系统无死锁。
