# FBBM 交付前剪切与成片替换设计

日期：2026-10-14。状态：R1，待 Grok 设计审查；不是已实现或已发布能力。

## 1. 目标与需求来源

目标：用户在上传 FBBM 前，通过帧范围删除不需要的内容，生成结果并检查；用户明确确认后，替换项目当前成片。界面始终只有一份当前成片，不要求用户管理历史版本。原视频是否保留属于后台恢复与存储策略，不等于 UI 展示多个版本。

### 已确定

- 先实现删除。保留“添加打码片段”按钮，只弹 toast，不生成打码操作。现有实验代码包含打码，不表示本期开放；旧打码草稿/任务不得被悄悄载入新删除方案。
- 在大弹窗内预览，时间轴紧接预览；以帧选择开始和结束，支持两端分别上一帧/下一帧微调。待处理列表和 AI 建议列表紧凑、最大高度内滚动。
- AI 建议只供选择，不自动删除。用户可手动添加删除片段。
- 生成不等于替换。预览后再次明确确认，才替换项目成片并上传项目用 OSS。
- 替换成功后不展示原成片/历史版本；播放、下载、再次编辑均使用新成片。
- 已交付 FBBM 的素材不允许再剪切或打码。这是交付前行为，不做“更新已交付视频”。
- 用户补充明确：旧项目中已经上传 FBBM 的素材卡片不展示“剪切与打码”入口，不展示置灰按钮，不为了剪切功能迁移这些已交付项目。
- 上传排队、执行中、结果待核实也锁定编辑，防止确认与实际交付之间视频变化。只有明确没有外部交付的失败，才可能恢复编辑。

### 尚未得到用户确认

- 旧正式成片保留 7 天、旧轻量预览保留 24 小时；这是建议值，不是删除授权。
- 未采用候选的保留期限建议 7 天，自最后一次有意义的用户操作算起；后台轮询不延长寿命。
- 第一版是否提供管理员恢复工具；用户端不提供历史列表。

在保留期限和清理实现通过单独验收前，自动删除开关必须关闭。磁盘不足时拒绝新生成，不以提前删旧成片解决空间问题。

## 3. 第一性原理：四种身份

1. **业务素材身份**：项目 ID + request_id。剪切不创建另一张业务卡片。
2. **内容身份**：一份不可变正式视频的 hash 与 version_id。内容变化就产生新内容身份；文件名是显示/交付命名，不是内容唯一标识。
3. **派生关系**：预览、帧缓存、扫描结果均绑定具体 master hash；删除计划绑定来源 version_id/hash。
4. **交付身份**：一次交付记录绑定明确 version_id/hash；交付开始后不能继续修改此业务素材的成片。

“替换”定义为原子切换业务素材的 current 引用，而不是覆盖原视频字节。
“隐藏旧视频”定义为普通用户只从 current 获取媒体，没有历史列表或旧会话恢复入口；不承诺撤回浏览器已下载的字节或立即吊销已签发的 OSS URL。

## 4. 推荐结构与实施边界

使用现有 material-media-state 作为唯一权威提交。剪切候选使用现有 versions 存储结构和封存目录，增加来源信息与用户确认步骤。不要同时维护一个独立 cut_current 指针。

### 4.1 旧项目

已上传 FBBM 的旧素材直接隐藏入口，不进入剪切接入流程；全部素材已交付的旧项目无需任何迁移。混合项目逐素材决定入口：已交付行隐藏、未交付行才有编辑资格，但现有 enroll 是项目级操作，因此不能因一行可编辑就静默迁移整项目。混合项目接入需保持已交付行及其回执完全不变，独立验收通过前只对已准备好的项目开放入口。

不在用户打开剪切时自动纳管，不全局打开 material_lifecycle 开关。仅对确需编辑且符合条件的旧项目，先做一个显式、幂等的接入流程：

- 保留现有 enroll 的静止、文件 hash、预览关联、交付一致性检查。
- 接入前检查真实任务与子进程，不只看 executor_running；排空同项目旧 worker，确认运行二进制支持纳管隔离。
- 旧项目仍有无法核实的交付/缺失文件/冲突记录时拒绝接入并解释原因。
- 接入后，读写/制作/审批必须走既有 managed 路径，不允许配置关闭后又降级旧流程。
- **开放前置条件**：纳管项目的后续制作与 FBBM 交付路径必须已经通过验收并可用，不能为剪切而让一个原来可上传的项目失去上传能力。现有 delivery_enabled=false 的环境只能验收生成/替换，不宣称交付闭环可用。
- 第一轮只在隔离副本验证接入，不擅自迁移日常 dev 数据或生产项目。若纳管交付暂不能上线，则剪切替换暂不开放生产；不引入临时覆盖原文件方案绕过。

### 4.2 现有制作候选与剪切候选

复用一个 asset.candidate_version 槽位。存在制作候选时禁止开始剪切候选；存在剪切候选时“重新制作”必须明确取消它，并增加代次让旧任务失效。不可两个候选竞争 current。

新增候选 origin_kind=postprocess 与 promotion_policy=manual（均为提议字段）。普通制作沿用现有自动提交策略；剪切完成不得进入普通 stage_finish 的自动切换分支。来源快照、代次、candidate ID 和 attempt 身份参与每次提交检查。

## 5. 数据契约提案（非当前已实现 API）

仍用 schema_version=1，新增字段必须先做向后兼容审查。旧二进制不能被允许写入新剪切状态；开关关闭仅阻止新操作，不能禁用读 current 和恢复已接受任务。

| 对象 | 提案字段/含义 |
| --- | --- |
| 剪切版本 | origin_kind=postprocess；source_version_id；source_sha256；ranges；recipe_sha256；promotion_policy=manual |
| 执行身份 | 复用 generation、execution attempt/process token；每次重试独立输出目录 |
| 候选状态 | queued → processing → ready_for_review；失败 failed；失效 superseded；确认后 current |
| 替换操作 | mutation_id、payload_sha256、source_version_id、candidate_version_id、actor、accepted_at、status/result；由现有 mutations/outbox 持久化，不靠内存线程 |
| 历史版本 | replaced_at；retention_until；媒体文件 live/pending_delete/deleted；保留 hash/来源/操作审计 |
| 清理任务 | 固定对象身份（本地路径+文件身份或 bucket+key+hash）、引用检查代次、not_before、状态、结果；不得只凭文件名或目录年龄 |

来源 version 引用不意味着永久保留全部祖先字节：已完成候选保存来源元数据即可；未完成的渲染、活跃编辑会话或恢复操作必须对来源文件保有运行期引用。永久元数据谱系与运行期字节依赖分开计数。

服务端只接收已验证的素材/版本/任务 ID，路径和 OSS key 从服务器权威状态解析。客户端不能提交任意文件路径、bucket、key 或新 SHA 来指定替换对象。

## 6. 交付前编辑锁

锁定范围为当前业务素材，不扩大到同项目其他未交付素材。

| 事实状态 | 可否编辑/生成/替换 |
| --- | --- |
| 从未提交交付，且无运行中的制作候选 | 可以 |
| 本地准备失败，已证明未发出外部写入、没有遗留回执 | 可以；统一后台判定，不由 UI 根据 failed 字样猜测 |
| pending/upload_queued/uploading/fbbm_queued | 不可以 |
| unverified、pending intent、核实中、无法确定是否发生外部效果 | 不可以 |
| 已有成功交付事实或外部对象/队列回执，尚未完成 FBBM | 不可以 |
| fbbm_ready | 永久禁止该素材剪切/打码，即使之后查询报错也不解锁 |

复用 delivery_blocked 与既有交付事实，建立统一服务端 eligibility 检查。不要把 publish_failed 一律当作可编辑。检查所有 deliveries，而不是只看最新一条；legacy 接入时检查 publications/intent/receipt/verification 历史。

展示规则：已交付的旧素材与新素材均不渲染剪切入口；不能仅依据当前制作状态 qc_passed 判断未交付。后台汇总真实交付事实返回能力，混合项目不一刀切隐藏未交付行。上传在途也不提供可操作的编辑入口。

入口至少覆盖：打开会话、读旧会话、帧/原片访问、自动扫描、新建渲染、重试、替换接受与最终提交；UI 根据服务端 can_edit/reason 展示，刷新前已经打开的弹窗也不能绕过。

### 上传与替换竞争

- 上传接受与替换接受在同一父 media lock 下互斥提交。锁内只做状态检查、CAS、写入意图，不跑网络、hash、FFmpeg。
- 上传先接受：交付锁事实落盘；随后编辑/替换拒绝。已有渲染即使完成也不能成为 current，候选标失效或仅待清理。
- 替换先接受：持久化 replacement_pending，上传接受拒绝；候选上传/核验在锁外进行。
- 替换最终提交时再次核对 current/source hash、候选/代次、交付锁、项目未删除/归档、操作仍有效。任一变化都不切换。
- 替换失败：旧 current 不动；显式失败并释放本次 pending。进程中断先进入恢复检查，不按超时直接放行上传。
- 普通制作用于切换 current 的最终提交，也必须遵守交付锁，不能通过重制绕过编辑禁令。

UI 保留未采用候选时，用户点击上传 current 应明确提示“有未采用的编辑结果，本次上传仍为当前成片”，并允许返回检查；上传接受后候选失效。禁止静默交付用户以为已经替换的新视频。

## 7. 删除、生成与预览

UI 帧号 1-based，首尾包含；服务端统一 [start,end) 0-based。例如 11–20 帧转为 [10,20)，删除 10 帧。排序并合并重叠/相邻范围，最多 40 段，不允许删光。编辑计划永远针对同一来源快照，不边编辑边重编号。

生成管线：校验来源 → 按原帧删除并同步剪音频 → 核验解码/帧数/音画时长 → 生成新轻量预览 → 核验 preview 来源 hash → 封存 master/preview → ready_for_review。

新的 QC 描述实际输出与剪切计划；不得继承原成片 expected_duration、旧安全检查结果、旧 playback approval。审核 AI 是抽样建议，不是新视频“安全通过”证据。

本期请求中的 mosaics 非空应明确拒绝；旧实验打码结果不作为删除候选自动恢复。服务端接口不能因 UI 按钮只弹 toast 而继续对正式用户开放打码。

帧性能：拖动走浏览器视频 seek，停下后约 200ms 再取精确帧；一次在途请求、过期结果丢弃，浏览器有限缓存；复用后端相邻 32 帧预取、128 帧缓存。缓存键包含源 hash。准确帧读取失败时显示状态，不把视频近似 seek 标成精确帧。首次全尺寸视频加载与 OSS Range 行为必须实际测速，不能以缓存设计保证公网性能。

## 8. 用户确认替换与后台事务

确认文案：“替换后，项目播放和下载将使用这份编辑后视频。”有旧文件保留政策时可以补充后台恢复期限；不展示历史列表，不暗示可在 UI 撤销已清理文件。

1. 服务端验证权限、CSRF、功能开关、项目可编辑、无交付锁、候选 ready_for_review、source=current。
2. 以 mutation_id 和完整正文摘要持久化替换操作及 outbox。重复同内容返回同一操作；相同 ID 不同正文拒绝。
3. 后台取得真实任务 attempt；核验封存文件，上传 master 与 preview 到项目私有哈希 key。开发环境不得用生产凭据；仅本地替换验收时响应明确 storage=local，不伪造 OSS 回执。
4. 上传成功但响应丢失，先查确切 key 的元信息/大小/hash/ACL；可确认同对象则继续，不能凭客户端超时判定失败，也不写交付对象。
5. 两个文件都就绪后，在同一父状态原子提交中切换 current、记录旧版 replaced_at/保留期限、清掉 candidate、完成 mutation、增加 revision、失效旧播放确认。
6. 返回项目最新 revision 和当前版本标识；客户端刷新权威项目详情。丢响应后重复请求/刷新得到已完成结果，不再切第二次。
7. 普通用户的旧 session/source/frame/output/scan 访问因 source 不再是 current 而拒绝；不靠前端隐藏达到禁用。新编辑创建新来源会话，不载入旧帧号、AI 建议或删除计划。

OSS 签名 URL 已发出最长 900 秒，替换不能撤回已下载媒体。旧预览延迟回收照顾切换前请求，不让旧 URL 长期成为正常入口。

## 9. 原视频与预览的保留、恢复和清理

### 9.1 决策原则

- 当前 master + preview 永不按历史 TTL 清理。
- 有运行任务、有效编辑租约、替换/恢复事务、法律/人工保留标记引用的文件不删。
- 剧集原素材独立管理，不受这次替换影响。
- 历史 master 可短期保留用于恢复；预览可从 master 重建，TTL 可更短。
- 旧元数据记录保留，清理删除的是大文件，不删必要审计事实。
- 元数据存在但文件已清理时显式标记 unavailable，不对用户声称可恢复。

### 9.2 待确认策略表

| 类型 | 建议期限 | 起算点 | 当前授权状态 |
| --- | --- | --- | --- |
| 被替换旧 master（本地与私有 OSS） | 7 天 | 成功替换提交时间 | 待用户确认；自动删除关闭 |
| 被替换旧 preview（本地与私有 OSS） | 24 小时 | 成功替换提交时间，且晚于已签 URL 宽限 | 同上 |
| 未采用候选/失败残留 | 7 天 | 最后有效操作或任务终止时间 | 同上 |
| 精确帧缓存 | 有界 LRU，可重建 | 会话失效后可回收 | 与正式媒体清理隔离 |

剪切会话当前还会创建 `cuts/<session>/source.mp4` 的独立复制件，任务输出和 partial 文件也会占空间。清理清单必须包含这些副本：运行任务的来源快照仍受引用保护；任务终止、会话失效后，不应让快照独立无限保留。封存输出必须有真实复制或受控移动的完成证据，才能清理 scratch；禁止硬链接到仍可被旧 worker 改写的文件。统计用量应覆盖 master、preview、cuts 快照、候选、partial、封存副本，不能只统计当前成片大小。

同一个 master 内容可能在多个版本引用，预览/master 也可能 hash 相同，实际 OSS key 可能相同。不能“按版本删一遍”就认为对象无引用。按真实物理对象聚合引用，本地文件也检查软链、硬链/封存来源规则。

### 9.3 清理协议提案

1. 只扫描本服务拥有的封存目录与项目私有 OSS 命名空间，不能扫描/删除 fb-bm-assets 交付 key，不改 bucket 生命周期策略。
2. 建立全量引用视图：当前版本、候选、运行任务/租约、恢复、交付、未决操作、历史保留。登记缺失/损坏时停止该命名空间清理，不将“读取失败”当作零引用。
3. 在与所有新引用建立入口相同的权威锁下复查，提交具体对象 pending_delete/tombstone 与任务；自此禁止签发新 URL、恢复或新增该对象引用。若上传重用同一 key，必须先通过同一协调器处理删除状态，不能绕过 tombstone。
4. 锁外执行删除，使用确定 bucket/key/hash 或受限绝对路径。对象 key 不允许可变覆盖；远端身份不符即停止。避免“HEAD 后对象已换”的窗口，依赖内容 key 不可变及引用/删除互斥规则。
5. 分别记录本地/OSS 删除完成，部分失败幂等重试；已删除对象可视为成功。失败不擦除墓碑和审计。
6. 清理中断后依据任务继续，不把状态倒回 live。手动恢复与 pending_delete 竞争只能有一方成功；恢复获得引用后清理拒绝，删除占位后恢复不能承诺成功。

**交付分期**：第一版替换不启用自动清理。必须先完成对现有 preview_oss `_ensure_uploaded`、签名、save_receipt、纳管、freeze、恢复、交付复制等所有引用入口的审计与并发测试，再交付清理协调器。当前 helper 没有删除接口，不为省事直接在它里加 delete_object。也不提前写入会失真的“已清理”状态。

管理员恢复（若实施）：同样需要未交付、无在途操作；验证旧 master 存在且 hash 正确，重新生成/上传 preview，作为新的显式候选经确认切换。禁止直接把 current 指针回拨到缺 preview/缺 OSS 的旧记录。

## 10. 拟议 HTTP 契约

以下是设计的新契约，不是已部署接口；实现前需与现有 material HTTP 路由合并评审，避免另建一套权限入口。

- 现有 cuts/open：增加 eligibility 与来源 current 检查；响应能力 can_edit + reason_code（新字段）。读旧会话必须验证所属素材当前来源。
- 现有 cuts/{session}/render：继续 ranges 协议，本期拒绝非空 mosaics；改为受控耐久任务和纳管候选，不能仅启动 daemon thread。
- 新 cuts/{session}/replace：POST `{job_id, source_version_id, revision, mutation_id}`；202 返回 `{operation_id,status}`。字段均是提案，来源由服务端交叉验证。
- 新 replacement 操作查询：GET 返回 `{operation_id,status,error_code?,current_version_id?,revision?,storage}`；status 为 pending/running/completed/failed/superseded。查询不触发新的替换。
- 错误分类：403 无操作权限/CSRF；404 不属于项目的素材/会话；409 当前版本变化/交付锁/候选冲突；422 范围非法/本期不支持打码；503 上传或资源暂不可用。错误不返回凭据、签名 URL、内部路径。
- 旧 save 入口不能作为替换别名；正式 UI 移除其版本语义。已有 saved 状态保持可读兼容，不自动导入 current。

## 11. 并发、崩溃与恢复验收

| 故障/竞争 | 预期 |
| --- | --- |
| 渲染失败、预览失败、任一 OSS 上传失败 | current 和原媒体完全不变，候选可解释地失败 |
| 接受替换后宕机、outbox 未投递 | 重启恢复同一操作，无重复候选 |
| 上传成功回执丢失 | 查同一私有 key，核验后继续 |
| master 上传成功、preview 失败 | 不切换，不继承旧 preview；可补传 |
| commit 成功 HTTP 响应丢失 | 幂等重试返回成功，当前唯一 |
| 两个浏览器替换不同候选 | 至多一份成功，另一份冲突 |
| 上传 FBBM 与替换同时提交 | 只有先持久化意图的一方推进 |
| 同素材历史 delivery 已成功，最新状态报错 | 仍不能编辑 |
| 旧候选/旧 worker 迟到、切换中删除/归档 | 代次/attempt/项目状态失配，不提交 |
| 旧 UI 保存打码草稿、新 UI 恢复 | 不生成打码；明确提示不支持 |
| 清理与恢复/签名/新引用并发 | 墓碑或新引用在同一协调域决定先后，无悬空 current |
| 一个物理 OSS key 被多个版本引用 | 任何有效引用存续时不删除 |
| JSON 损坏、注册表缺失、旧二进制回滚 | fail-closed，不回退旧成片路径或绕开交付锁 |

测试层次：纯状态机/帧区间单测；真实 FFmpeg 合成帧序列和音轨验证；HTTP ACL/CSRF/重复提交测试；真实多进程锁和崩溃注入；浏览器预览/端点微调/刷新/旧会话验证；隔离 OSS 桶/前缀验证上传及清理。模拟桶测试不等于真实 OSS 成功，未真实交付不得声称 FBBM 已验证。

## 12. 实施顺序与模块边界

本文件是业务与架构设计，不是执行授权或逐行实现计划。实现继续前先完成设计审查及保留策略确认。

1. **交付锁与契约**：`material_versions.py`、`workflow.py`、`cutting_http.py` 统一 eligibility；写失败测试覆盖已交付/队列/unknown/明确无效果失败。确认 legacy 与 managed 映射，不能按猜测状态实现。
2. **隔离接入与候选**：通过既有 enroll 纳管隔离夹具；`material_workers.py` 增加手动确认候选策略，保持现有制作自动策略；真实任务 attempt、磁盘预算与恢复。
3. **删除生成**：`cutting.py` 和 `preview.py` 生成并封存成对媒体；旧 daemon 实验转换为耐久调度，不调用外部交付。
4. **用户确认替换**：复用 `preview_oss.py` 内容寻址上传；新增独立协调模块（建议 `cutting_replace.py`）只负责编排，权威提交仍在 media-state；网页按操作查询与 current 刷新。
5. **验收与有限开放**：所有入口使用同一来源解析和锁规则；检查生产开关/旧项目接入/新版交付可用性。未确认上线范围不迁移生产。
6. **保留与清理另一期**：用户确认期限后，设计并实现共享对象引用/墓碑协调器、dry-run 清单、清理审计和恢复；先报告再开启自动删除。

Python 测试使用 `~/miniconda3/envs/py3.12/bin/python3.12`。实现遵守现有 load_config 配置机制，不新增临时环境变量绕过中央配置。schema 兼容、部署恢复和旧二进制写入阻断需独立验收。
